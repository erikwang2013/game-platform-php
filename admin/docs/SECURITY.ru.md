## 1. Панорама эшелонированной обороны

Система использует модель 7-уровневой эшелонированной обороны: злонамеренные запросы фильтруются снаружи внутрь уровень за уровнем, гарантируя, что при отказе любого отдельного уровня остаются последующие линии защиты.

Вся цепочка промежуточного ПО выполняется в следующем порядке (см. `config/middleware.php`):

```
请求 → Cors → SecurityFilter → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| Уровень | Промежуточное ПО/механизм | Цель защиты |
|----|--------|---------|
| 1 | SecurityFilter | Блокировка XSS / SQL-инъекций / обхода пути / инъекций команд / CSRF-атак |
| 2 | Cors | Безопасность CORS + внедрение защитных заголовков ответа |
| 3 | RateLimit | Скользящее окно Redis, защита от брутфорса |
| 4 | AdminAuth | JWT-аутентификация + выход через черный список |
| 5 | AdminPermission | RBAC-авторизация с гранулярностью method.path |
| 6 | OperationLog | Аудит операций + отслеживание источника |
| 7 | Шифрование данных | Обефускация ID через Hashids + шифрование БД Encryptable + шифрование передачи EncryptionService |

Фронтенд (Flutter) имеет собственные независимые проверки ввода на трех уровнях, бэкенд не доверяет им, каждый уровень защищается независимо.

## 2. Механизм обнаружения атак

### 2.0 Ограничение HTTP-методов

SecurityFilter первым делом проверяет HTTP-метод до всех проверок атак, разрешены только следующие стандартные методы:

```
GET, POST, PUT, DELETE, OPTIONS, HEAD
```

Нестандартные методы (например, TRACE, CONNECT, PATCH, пользовательские методы и т.п.) сразу возвращают **405 Method Not Allowed**, тело ответа — пустой HTML, дальнейшее обнаружение атак и бизнес-логика не выполняются.

Это первая линия эшелонированной обороны, эффективно блокирующая:
- Атаки XST через TRACE
- Злоупотребление CONNECT-туннелями
- Пробы нестандартных WebDAV-методов
- Перебор HTTP-методов автоматическими сканерами

### 2.1 XSS (межсайтовые сценарии)

Все регулярные выражения взяты из `SecurityFilter::PATTERNS['XSS']`, сопоставление без учета регистра.

| Паттерн обнаружения | Регулярное выражение | Защищаемая атака |
|----------|------|-----------|
| Теги скриптов | `<\s*\/?\s*s\s*c\s*r\s*i\s*p\s*t\b` | `<script>`, `<script >`, `< script>` и другие варианты с пробелами |
| Атрибуты событий | `\bon\w+\s*=\s*[\"\']?\s*(?:javascript\|vbscript):` | `onclick="javascript:..."` и другие встроенные события |
| JS-псевдопротокол | `(?:javascript\|vbscript)\s*:\s*(?:[^\s]*\s*)?(?:eval\|alert\|prompt\|confirm\|document\.cookie\|location\s*=)` | `javascript:eval(...)`, `javascript:alert(1)` и т.п. |
| XSS через Data URI | `data\s*:\s*text\s*\/\s*html\s*(?:;base64)?\s*,` | `data:text/html,<script>`, `data:text/html;base64,...` и т.п. |
| Инъекция шаблонов | `\{\{.*?\}\}` | `{{constructor}}`, `{{7*7}}` — инъекции шаблонов серверных/Angular/Vue |

### 2.2 SQL-инъекции

| Паттерн обнаружения | Регулярное выражение | Защищаемая атака |
|----------|------|-----------|
| UNION-запросы | `\bUNION\s+(?:ALL\s+)?SELECT\b` | `UNION SELECT`, `UNION ALL SELECT` — выгрузка базы |
| OR с вечной истиной | `(?:[\"\']\s*OR\s+[\"\']?\s*\d+\s*=\s*\d+\|[\"\']\s*OR\s+[\"\']?1[\"\']?\s*=\s*[\"\']?1)` | `' OR 1=1--`, `" OR '1'='1'` |
| Разрушение структуры | `\b(?:DROP\|ALTER\|TRUNCATE)\s+(?:TABLE\|DATABASE\|INDEX\|VIEW)\b` | `DROP TABLE users`, `TRUNCATE TABLE logs` |
| Вызов хранимых процедур | `\b(?:xp_cmdshell\|sp_executesql\|sp_addsrvrolemember)\b` | Выполнение команд через расширенные хранимые процедуры MSSQL |
| Проба метаданных | `\b(?:INFORMATION_SCHEMA\|sys\.(?:tables\|columns\|databases)\|pg_class\|sqlite_master\|mysql\.(?:user\|db))\b` | Проба структуры БД MySQL/PG/SQLite/MSSQL |
| Обход через комментарии | `(?:[\"\'])\s*(?:--\|#)\s*[\"\']?\s*(?:OR\|AND\|SELECT\|INSERT\|UPDATE\|DELETE\|DROP)` | `'-- OR SELECT`, `'# AND UPDATE` — обход через комментарии |

### 2.3 Обход пути

| Паттерн обнаружения | Регулярное выражение | Защищаемая атака |
|----------|------|-----------|
| Возврат по каталогам | `\.\.[\/\\\\]{2,}` | `../`, `..\`, `....//` — многоуровневый возврат по каталогам |
| Проба чувствительных файлов | `\/(?:etc\/(?:passwd\|shadow\|hosts)\|proc\/self\|boot\.ini\|win\.ini\|WEB-INF\|\.env\|\.git\/)` | `/etc/passwd`, `/proc/self/environ`, `.env`, `.git/HEAD` и т.п. |
| Усечение нулевым байтом | `%00` | `../../../etc/passwd%00.jpg` — обход проверки расширения |

### 2.4 Инъекции команд

| Паттерн обнаружения | Регулярное выражение | Защищаемая атака |
|----------|------|-----------|
| Команды через конвейер/точку с запятой | `[;\|&]\s*(?:ls\|cat\|rm\|wget\|curl\|nc\|bash\|sh\|cmd\|powershell\|python\|perl)\b` | `;cat /etc/passwd`, `\|bash` |
| Подстановка в обратных кавычках | `` `[^`]*\b(?:cat\|ls\|id\|whoami\|pwd\|rm\|wget\|curl)\b[^`]*` `` | `` `cat /etc/passwd` `` |
| Подстановка $() | `\$\(\s*(?:cat\|ls\|id\|whoami\|rm\|wget\|curl)\b` | `$(whoami)`, `$(cat flag)` |
| Удаленная загрузка в конвейер | `(?:wget\|curl)\s+.*(?:\b-o\b\|\b-O\b\|pipe\|bash\|python).*\bhttps?:\/\/` | `wget URL -O - \| bash`, `curl URL \| python` |

### 2.5 CSRF (подделка межсайтовых запросов)

Логика проверки реализована в `SecurityFilter::checkCsrf()`:

```php
// 仅 POST/PUT/DELETE 触发校验
// Origin 头和 Referer 均为空 → 放行（非浏览器客户端）
// Origin 非空 → 解析 Origin 域名与 Host 比对
```

Правила сопоставления:
- Удалить префикс `www.` у Host и точно сравнить с доменом Origin
- Если Host является родительским доменом Origin (например, `Origin: app.example.com`, `Host: example.com` — срабатывает `str_contains($originHost, '.' . $hostOnly)`), пропустить
- Ни точное совпадение, ни поддомен → вернуть 403, квалифицировать как CSRF-атаку

Примечание: небраузерные клиенты (например, curl без Origin/Referer) пропускаются напрямую, защита CSRF эффективна только для браузерного окружения.

### 2.6 Злонамеренная загрузка файлов

| Паттерн обнаружения | Регулярное выражение | Защищаемая атака |
|----------|------|-----------|
| Маскировка двойным расширением | `\.(?:php\d?\|phtml\|phar\|cgi\|pl\|py\|jsp\|asp)x?\.(?:png\|jpg\|gif\|pdf)` | `shell.php.png`, `shell.phar.jpg` — обход белого списка |
| Расширение PHP | `\.php\s*$/m` | Передача пути `.php` непосредственно в параметрах запроса |

## 3. Эскалация атак и черный список IP

SecurityFilter имеет встроенный механизм эскалации атак для защиты от непрерывного сканирования с одного IP.

### Процесс эскалации

```
第 1 次扫描命中 → Redis INCR security_escalate:{ip} = 1, TTL=60s
第 2 次扫描命中 → INCR → 2
...
第 5 次扫描命中 → INCR → 5
    → 触发封禁: SETEX security_ban:{ip} 900 1
    → 清除计数器 DEL security_escalate:{ip}
    → 写入安全日志: [SECURITY] IP banned 15min
```

### Поведение в период бана

Каждый запрос при входе в SecurityFilter сначала проверяет `isBanned()`:

```php
if (Redis::get("security_ban:{$ip}")) {
    return response('<h1>403 Forbidden</h1>', 403);
}
```

Забаненный IP в течение 15 минут на все запросы (включая легитимные) получает сразу 403, последующая бизнес-логика полностью пропускается.

### Константы конфигурации

| Константа | Значение | Назначение |
|------|-----|------|
| ESCALATE_LIMIT | 5 | Порог срабатываний в 60-секундном окне |
| ESCALATE_WINDOW | 60 | Окно счетчика (секунды) |
| BAN_DURATION | 900 | Длительность черного списка (секунды), т.е. 15 минут |

### Журнал безопасности

Расположение файла: `runtime/logs/security.log`

Пример формата журнала:
```
2026-05-20 14:32:11 [SECURITY] XSS attack blocked | IP: 192.168.1.100 | Path: /admin/user | Field: body.username | Source: body | Payload: <script>alert(1)</script>
2026-05-20 14:32:15 [SECURITY] IP banned 15min | IP: 192.168.1.100 | Triggers: 5
```

### Ограничение размера тела запроса

`Content-Length > 10MB` сразу возвращает 413 Payload Too Large, защита от DoS-атак сверхбольшими телами запросов.

### Проверка Content-Type

Запросы POST/PUT **обязаны** объявлять `Content-Type` как `application/json` или `application/x-www-form-urlencoded`, иначе возвращается 415 Unsupported Media Type. Запросы загрузки файлов (с полем file) пропускают эту проверку.

## 4. Защитные заголовки ответа

Все заголовки внедряются в промежуточном ПО `Cors` через `$response->withHeaders()` и добавляются к каждому ответу.

| Заголовок | Значение | Назначение |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | Разрешение CORS с любого источника (сценарий интранет-панели) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | Разрешенный набор методов |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | Разрешенные пользовательские заголовки |
| Access-Control-Max-Age | `86400` | Кэш preflight-запросов 24 часа |
| X-Content-Type-Options | `nosniff` | Запрет MIME-сниффинга браузером |
| X-Frame-Options | `DENY` | Запрет встраивания в любые iframe, защита от кликджекинга |
| X-XSS-Protection | `1; mode=block` | Включение встроенного XSS-фильтра браузера с блокировкой рендеринга страницы |
| Referrer-Policy | `strict-origin-when-cross-origin` | При том же источнике — полный URL, при кросс-домене — только домен |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | Глобальный запрет API камеры/микрофона/геолокации |

Preflight-запросы OPTIONS возвращают пустой ответ 204 и не проходят дальше по цепочке промежуточного ПО.

### 4.2 Content-Security-Policy (CSP)

Вместе с другими защитными заголовками внедряется в промежуточном ПО Cors, обеспечивая эшелонированную оборону: ограничение источников ресурсов, которые браузер может загружать и исполнять.

| Заголовок | Значение | Назначение |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | Ограничение источников скриптов/стилей/изображений/соединений/фреймов/форм |
| X-Permitted-Cross-Domain-Policies | `none` | Запрет загрузки файлов кросс-доменных политик Adobe Flash/PDF и т.п. |

Ключевые пункты политики CSP:
- `default-src 'self'`: по умолчанию разрешены только ресурсы того же источника
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: разрешение скриптов того же источника + встроенных скриптов (обязательно для Flutter Web) + eval (обязательно для отладки Flutter Web)
- `frame-ancestors 'none'`: запрет встраивания в iframe на любых страницах, двойная страховка с X-Frame-Options: DENY
- `base-uri 'self'`: ограничение тега `<base>` только тем же источником
- `form-action 'self'`: ограничение отправки форм только на тот же источник

## 5. Стратегия ограничения частоты

### Алгоритм

Скользящее окно Redis Sorted Set + атомарный Lua-скрипт, ключевые операции:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua-скрипт выполняется на стороне Redis в одном потоке, **естественно атомарен**, устраняя гонки TOCTOU (Time-of-check to Time-of-use).

### Конфигурация ограничения частоты

| Маршрут | Лимит | Окно | Сценарий |
|------|------|------|------|
| По умолчанию (все маршруты) | 60 раз/мин | 60s | Обычные API |
| `/api/auth/login` | 10 раз/мин | 60s | Вход (защита от брутфорса) |
| `/api/auth/register` | 5 раз/мин | 60s | Регистрация (защита от массовой регистрации) |

### Заголовки ответа

При срабатывании лимита возвращается HTTP 429 с JSON-телом:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

Все ответы (включая нормальные) несут следующие заголовки:

| Заголовок | Описание |
|----|------|
| X-RateLimit-Limit | Максимальное число запросов в текущем окне |
| X-RateLimit-Remaining | Оставшееся число запросов в текущем окне |
| X-RateLimit-Reset | Unix-временная метка сброса окна |
| Retry-After | Есть только при срабатывании лимита, рекомендуемые секунды ожидания |

### Стратегия деградации

При сбое Redis (таймаут соединения, недоступность и т.п.) — **fail-closed**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    // Redis down: 限流不可用即拒绝，避免安全防线失效（登录/支付回调限流为空转）
    return json(['code' => 503, 'message' => '服务暂不可用，请稍后再试', 'data' => []])
        ->withStatus(503)->withHeaders(['Retry-After' => '5']);
}
```

Ограничение частоты — первая линия защиты от брутфорса при входе и от повторных платежных callback'ов; при отказе Redis запросы лучше отклонять (503), чем пропускать.

### 5.4 Механизм блокировки аккаунта

Интерфейс входа дополнительно к ограничению частоты имеет механизм **блокировки аккаунта**, защищающий от направленного брутфорса конкретного пользователя.

**Процесс блокировки**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**Поведение в период блокировки**:

В период блокировки все запросы входа сразу возвращают 429, проверка пароля не выполняется, попытки брутфорса полностью блокируются.

**Константы конфигурации**:

| Константа | Значение | Назначение |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | Максимальное число последовательных неудач |
| LOCKOUT_DURATION | 900 | Длительность блокировки (секунды), т.е. 15 минут |

Примечание: блокировка аккаунта основана на `userId`, а не на IP, поэтому смена IP не обходит блокировку. В сочетании с IP-лимитом (10 раз/мин) образуется двойная защита:
- На уровне IP: лимит 10 раз/мин блокирует распределенный брутфорс
- На уровне аккаунта: блокировка после 5 неудач блокирует направленный брутфорс

## 6. Аутентификация и авторизация

### 6.1 JWT-аутентификация

Реализована в промежуточном ПО AdminAuth, монтируется на группы маршрутов, требующих аутентификации.

**Параметры конфигурации** (`config/plugin/erikwang2013/jwt/jwt`, инжектируются из `.env`):

| Параметр | Значение | Описание |
|------|-----|------|
| Алгоритм | HS256 | Симметричная подпись HMAC-SHA256 |
| Ключ | `JWT_SECRET_KEY` | Инжектируется из переменной окружения, при отсутствии или значении по умолчанию **запуск отклоняется** (fail-closed) |
| TTL access_token | 7200s (2ч) | `JWT_TTL` |
| TTL refresh_token | 1209600s (14д) | `JWT_REFRESH_TTL` |
| Эмитент | `open-admin` | `JWT_ISSUER` |
| Аудитория | `open-admin` | `JWT_AUDIENCE` |

**Извлечение токена**: из заголовка `Authorization: Bearer <token>`, снятие префикса `Bearer ` дает исходный JWT.

**Процесс аутентификации**:
1. Пустой токен → сразу 401 `{"code": 401, "message": "未登录"}`
2. Проверка черного списка Redis `jwt_blacklist:{md5(token)}` → совпадение → 401 `Token已失效，请重新登录`
3. Декодирование JWT → ошибка (истек/не совпала подпись) → 401 `Token已过期或无效`
4. Успех → инжекция `$request->adminId` и `$request->adminUsername`

**Механизм черного списка**: при выходе пользователя `md5(token)` записывается в Redis с TTL, равным оставшемуся сроку действия JWT. При отказе Redis проверка черного списка пропускается (fail-open), тогда вышедший токен еще короткое время пригоден, но короткий срок самого JWT (2ч) служит страховкой.

**Обновление токена**: `POST /api/auth/refresh` проверяет исходный refresh token (`token_type=refresh`, не истек, не в черном списке), только затем выпускает новую пару, и проверяет, что `sub` — действительный ID пользователя — **refresh token с sub=null больше не выпускается**, при неудаче обновления сразу возвращается 401.

### 6.2 Ограничение параллельных сессий

Для защиты от злоупотребления украденным токеном на нескольких устройствах система ограничивает число действительных токенов одного пользователя.

**Логика ограничения**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**Константы конфигурации**:

| Константа | Значение | Назначение |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | Максимальное число параллельных токенов одного пользователя |

**Сценарий вытеснения**: при входе пользователя на 4-м устройстве токен 1-го устройства принудительно попадает в черный список, последующие запросы возвращают 401 "Token已失效，请重新登录".

При выходе текущий токен удаляется из набора. При естественном истечении токена ключ Redis автоматически теряет силу, члены набора уменьшаются.

### 6.3 Модель RBAC-прав

Реализована в промежуточном ПО AdminPermission.

**Модель данных**: трехслойная связь User -> Role -> Permission

- `game_admin_user` (таблица пользователей)
- `game_admin_user_role` (таблица связей пользователь-роль)
- `game_admin_role` (таблица ролей)
- `game_admin_role_permission` (таблица связей роль-право)
- `game_admin_permission` (таблица прав)

**Типы прав**:
| type | Значение | Пример |
|------|------|------|
| 1 | Право меню | Управление видимостью левой навигации |
| 2 | Право кнопки | Управление кнопками операций на странице (создание/редактирование/удаление) |
| 3 | Право API | Управление вызовами бэкенд-интерфейсов |

Формат идентификатора API-права: `{method}.{path}`

Например:
- `post.admin/user` — создание пользователя
- `put.admin/user` — редактирование пользователя
- `delete.admin/user` — удаление пользователя
- `get.admin/user` — просмотр списка пользователей

**Процесс авторизации**:
1. `$request->adminId` пуст (не вошел) → сразу 401 `{"code": 401, "message": "未登录"}`, пропуск больше не допускается
2. Получить пользователя → роли (пропуск отключенных ролей со `status=0`) → список прав
3. Супер-администратор (`slug = '*'`) → сразу пропустить
4. Построить `strtolower(method) . '.' . trim(path, '/')` → сравнить со списком прав
5. Совпадения нет → 403 `{"code": 403, "message": "无权限访问"}`

**Повторное подтверждение**: BaseController предоставляет метод `confirmPassword()`, чувствительные операции (удаление пользователя, экспорт данных и т.п.) на уровне контроллера дополнительно требуют ввода текущего пароля, защищая от неавторизованных операций после перехвата сессии.

### 6.4 Проверка подписи платежных callback'ов (fail-closed)

Проверка подписи `POST /api/payment/callback` (callback пополнений Stripe/PayPal) использует **fail-closed**: любой пропуск конфигурации или ошибка проверки отклоняет callback:

| Сценарий | Поведение |
|------|------|
| Stripe не настроен `STRIPE_WEBHOOK_SECRET` | Отклонение (403), callback без подписи больше не принимается |
| Подпись Stripe отсутствует / не прошла проверку | Отклонение (403) |
| Временная метка Stripe `t=` отсутствует или отклонение от времени сервера **> ±5 минут** | Отклонение (403), защита от повторного воспроизведения |
| PayPal не настроен `PAYPAL_WEBHOOK_ID` | Отклонение (403) |
| Ошибка обратной проверки PayPal / не SUCCESS | Отклонение (403) |
| При настроенном `CALLBACK_TRUSTED_IPS` IP источника не в белом списке | Отклонение (403) |
| Провайдер callback'а не совпадает со способом оплаты заказа / способ оплаты не существует | Отклонение (403) |

Зачисление по callback'у (обновление статуса + баланс + операции) выполняется в одной транзакции БД, при ошибке любого шага все откатывается, исключая частичное зачисление.

## 7. Журналы аудита

### 7.1 Журнал операций

Промежуточное ПО OperationLog автоматически записывает журнал операций для запросов POST / PUT / DELETE. Запросы GET не записываются.

**Записываемые поля**:

| Поле | Источник | Описание |
|------|------|------|
| id | SnowflakeService::generate() | Глобально уникальный ID |
| user_id | `$request->adminId` | ID оператора, при отсутствии входа — 0 |
| action | `$request->method()` | Эквивалентно методу |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | Путь запроса |
| ip | `$request->getRealIp()` | Реальный IP клиента |
| source | detectSource() | Платформа-источник клиента |
| input | тело запроса (JSON после деидентификации) | Отправленные данные операции |
| created_at | `date('Y-m-d H:i:s')` | Время операции |

**Фильтрация чувствительных полей**: при рекурсивном обходе тела запроса значения следующих полей заменяются на `***`:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**Определение источника** (`detectSource()`): по приоритету:

1. Сначала читается пользовательский заголовок `X-Client-Platform` (явно объявляется нативным клиентом)
2. Иначе — вывод по строке User-Agent (порядок проверки метода `detectSource()`):

| Платформа | Ключевые слова UA |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | Значение по умолчанию |

**Отказоустойчивость**: ошибка записи журнала не блокирует бизнес-запрос (`catch (\Throwable)` — тихое проглатывание).

### 7.2 Журнал безопасности

**Расположение файла**: `runtime/logs/security.log`

**Записываемое содержимое**:
- Журнал блокировок атак: категория атаки, IP, путь, поле, источник, фрагмент payload (первые 200 символов)
- Уведомления о бане IP: забаненный IP, число срабатываний

Права на запись журнала — `FILE_APPEND | LOCK_EX`, обеспечивающие безопасную запись при конкурентном доступе.

## 8. Защита данных

Система использует трехуровневую стратегию защиты данных, соответствующую трем этапам потока данных.

### 8.1 Транспортный уровень — EncryptionService

`EncryptionService` использует пакет `erikwang2013/encryption` для шифрования/дешифрования чувствительных полей в запросах/ответах API.

**Технические детали**:
- Алгоритм: `aes-256-cbc-hmac` (встроенная подпись HMAC против подделки)
- Ключ: переменная окружения `ENCRYPTION_KEY`, автоматически выравнивается до 32 байт
- Назначение: передача между клиентом и API таких полей, как телефон, номер удостоверения личности

**Вспомогательные методы деидентификации**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (имя пользователя длиннее 2 символов) или `a**@example.com`

### 8.2 Уровень хранения — Cast Encryptable

Модель `AdminUser` использует Eloquent cast `Erikwang2013\Encryptable\Encryptable`, соответствующие поля:

- `email` → cast в Encryptable, автоматическое шифрование/дешифрование
- `phone` → cast в Encryptable, автоматическое шифрование/дешифрование
- `id_card` → cast в Encryptable, автоматическое шифрование/дешифрование

При записи в БД автоматически шифруется в шифротекст, при чтении автоматически дешифруется в открытый текст. Тип колонки хранения — `VARCHAR(500)`, шифротекст хранится в base64.

**Система ключей**: независимо от транспортного шифрования (`ENCRYPTION_KEY`) используется `ENCRYPTABLE_KEY`; утечка одного ключа не выводит из строя другой уровень.

Ротация ключей: переменная окружения `ENCRYPTION_PREVIOUS_KEYS` поддерживает список исторических ключей (через запятую); при чтении старых данных пробуются исторические ключи, при записи данные перешифровываются текущим ключом.

### 8.3 Уровень отображения — обефускация ID и деидентификация

**Обефускация ID через Hashids**: `HashidsService` использует пакет `erikwang2013/hashids`.

- Возвращаемые внешним API BIGINT ID из БД кодируются в hash-строки (например, `xK3mN9qR2pL7wV8b`)
- Клиент передает hash-строки, бэкенд автоматически декодирует их в исходные ID
- Соль `HASHIDS_SALT` инжектируется из переменной окружения, разные соли дают полностью разные результаты кодирования/декодирования
- Минимальная длина hash — 16 символов, используется 62-символьный буквенно-цифровой набор
- BaseController предоставляет удобные методы `encodeId()`, `decodeId()`, `encodeIds()`

**Деидентификация при экспорте**: при экспорте Excel/PDF (ExportController) чувствительные поля единообразно деидентифицируются:
- Телефон: `138****1234`
- Email: `a***@example.com`
- Удостоверение личности: полностью закрывается как `********`

## 10. security.txt (RFC 9116)

Система предоставляет на `/.well-known/security.txt` эндпоинт контактной информации безопасности по стандарту RFC 9116, чтобы исследователи безопасности могли быстро найти канал сообщения об уязвимостях.

**Способ доступа**:

```
GET /.well-known/security.txt
```

**Содержимое ответа**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**Описание полей**:

| Поле | Описание |
|------|------|
| Contact | Контакты для сообщения об уязвимостях безопасности |
| Expires | Время истечения файла, требует регулярного обновления |
| Preferred-Languages | Предпочитаемые языки общения |
| Canonical | Канонический URL этого файла |
| Policy | Ссылка на политику безопасности/раскрытия уязвимостей |

Этот эндпоинт не ограничен промежуточным ПО (лимит частоты, аутентификация и т.п.), доступен всем напрямую.

## 11. Конфигурация безопасности Nginx

Проект предоставляет `docs/nginx-security.conf` как эталонную конфигурацию усиления безопасности обратного прокси Nginx для продакшена.

**Включенные меры безопасности**:

| Пункт конфигурации | Назначение |
|--------|------|
| `server_tokens off` | Скрытие номера версии Nginx |
| `client_max_body_size 10m` | Ограничение размера тела запроса, совместно с SecurityFilter |
| `limit_req_zone` | Ограничение частоты запросов на уровне Nginx |
| `limit_conn_zone` | Ограничение числа параллельных соединений |
| `add_header` защитные заголовки | Добавление на уровне Nginx таких заголовков, как X-XSS-Protection |
| `if ($request_method)` | Отклонение нестандартных HTTP-методов на уровне Nginx |
| Конфигурация SSL/TLS | Современные настройки TLS 1.2/1.3, отключение слабых шифр-наборов |
| Скрытие заголовков бэкенда | `proxy_hide_header` удаляет чувствительные заголовки вроде версии webman |

**Использование**: объедините конфигурацию из `docs/nginx-security.conf` в свой блок server Nginx, скорректируйте под фактический домен и пути к сертификатам.

## 12. Модель угроз

### 12.1 Защищенные угрозы

| Тип угрозы | Вектор атаки | Уровень защиты |
|----------|---------|---------|
| Злоупотребление HTTP-методами | TRACE/TRACK XST, CONNECT-туннели, пробы WebDAV-методов | Белый список методов SecurityFilter 405 (GET/POST/PUT/DELETE/OPTIONS/HEAD) |
| Направленный брутфорс | Многократные попытки пароля конкретного пользователя | Блокировка аккаунта (5 неудач — блокировка 15 минут) + RateLimit (вход 10/мин) + Captcha |
| Брутфорс | Распределенные IP многократно пробуют имена/пароли | RateLimit (вход 10/мин) + Captcha |
| XSS | `<script>`, onerror, javascript: | SecurityFilter (5 паттернов) + заголовок X-XSS-Protection + CSP |
| SQL-инъекции | UNION SELECT, OR 1=1, обход через комментарии | SecurityFilter (6 паттернов) + параметризованные запросы Eloquent ORM |
| CSRF | Подделка запросов со злонамеренных сайтов | Проверка Origin/Referer в SecurityFilter |
| Обход пути | `../../etc/passwd` | Паттерн обхода пути в SecurityFilter + белый список расширений UploadController |
| Инъекции команд | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityFilter (4 паттерна) |
| Перехват сессии | Кража JWT-токена | Короткий срок JWT (2ч) + выход через черный список + повторное подтверждение паролем чувствительных операций |
| Перебор ID | Перебор числовых ID для угадывания объемов данных | Обефускация Hashids в случайные строки |
| Утечка данных | Выгрузка БД / посредник / утечка журналов | Трехуровневое шифрование/деидентификация + фильтрация чувствительных полей OperationLog |
| DoS | Сверхбольшие тела запросов / высокая частота | Лимит тела 10MB + RateLimit 60/мин + черный список IP |
| Повышение прав | Обращение низкопривилегированных пользователей к интерфейсам панели | RBAC-авторизация с гранулярностью method.path |
| Атаки загрузки файлов | Двойное расширение shell.php.png | Обнаружение злонамеренных файлов в SecurityFilter |

### 12.2 Известные ограничения

| Ограничение | Сфера влияния | Меры смягчения |
|------|---------|---------|
| Защита CSRF действует только для браузеров | Небраузерные клиенты (curl, Postman, мобильные приложения) могут обойти проверку Origin/Referer | Небраузерные клиенты по своей природе не подвержены CSRF; вместо Cookie используется JWT-аутентификация |
| При отказе Redis: лимит частоты fail-closed (503), проверка черного списка fail-open | Часть запросов отклоняется при лимитировании; вышедший токен короткое время пригоден | Мониторинг доступности Redis с алертами; короткий срок JWT как страховка |
| Нет отдельного WAF-движка | SecurityFilter использует сопоставление `@preg_match` регулярными выражениями, а не специализированный движок правил WAF | В проде рекомендуется Nginx ModSecurity или Cloudflare WAF на переднем крае |
| JWT без состояния не может быть принудительно отозван | До истечения токена нет способа отозвать его на сервере (кроме черного списка) | Черный список + короткий TTL 2ч уменьшают окно риска |
| Черный список IP хранится только в памяти | После перезапуска Redis черный список теряется | Длительность бана всего 15 минут, влияние ограничено |
| Нет особого лимита для админ-эндпоинтов | Админ-интерфейсы используют общий лимит 60/мин по умолчанию | Частота операций администратора естественно низкая, пока разделение не требуется |
| `@preg_match` подавляет ошибки | При некорректном регулярном выражении тихо выходит из строя | `preg_last_error()` можно покрыть мониторингом, пока не реализовано |
