## 1. गहराई-रक्षा परिदृश्य

सिस्टम 7-परत गहराई-रक्षा मॉडल अपनाता है, बाहर से अंदर तक हर परत दुर्भावनापूर्ण अनुरोधों को छानती है, यह सुनिश्चित करते हुए कि किसी भी एक परत की विफलता पर आगे की रक्षा पंक्तियाँ बनी रहती हैं।

पूरी मिडलवेयर श्रृंखला निम्न क्रम में चलती है (`config/middleware.php` देखें):

```
请求 → Cors → SecurityFilter → RateLimit → [路由组中间件: AdminAuth → AdminPermission → OperationLog] → Controller
```

| परत | मिडलवेयर/तंत्र | सुरक्षा लक्ष्य |
|----|--------|---------|
| 1 | SecurityFilter | XSS / SQL इंजेक्शन / पाथ ट्रैवर्सल / कमांड इंजेक्शन / CSRF आक्रमण अवरोध |
| 2 | Cors | क्रॉस-ओरिजिन सुरक्षा + प्रतिक्रिया सुरक्षा हेडर इंजेक्शन |
| 3 | RateLimit | Redis स्लाइडिंग विंडो दर सीमा, ब्रूट-फोर्स रोकथाम |
| 4 | AdminAuth | JWT प्रमाणीकरण + ब्लैकलिस्ट लॉगआउट |
| 5 | AdminPermission | RBAC method.path ग्रैन्युलैरिटी प्रमाणीकरण |
| 6 | OperationLog | ऑपरेशन ऑडिट + स्रोत ट्रैकिंग |
| 7 | डेटा एन्क्रिप्शन | Hashids ID अस्पष्टीकरण + Encryptable DB एन्क्रिप्शन + EncryptionService ट्रांसमिशन एन्क्रिप्शन |

फ्रंटएंड तीन परतें (Flutter) की अपनी स्वतंत्र इनपुट सत्यापन है, बैकएंड भरोसा नहीं करता, हर परत स्वतंत्र रूप से रक्षा करती है।

## 2. आक्रमण पहचान इंजन

### 2.0 HTTP विधि सीमा

SecurityFilter सभी आक्रमण पहचान से पहले HTTP विधि सत्यापित करता है, केवल निम्न मानक विधियाँ अनुमत:

```
GET, POST, PUT, DELETE, OPTIONS, HEAD
```

गैर-मानक विधियाँ (जैसे TRACE, CONNECT, PATCH, कस्टम विधियाँ) सीधे **405 Method Not Allowed** लौटाती हैं, प्रतिक्रिया निकाय खाली HTML होता है, आगे की आक्रमण पहचान या व्यावसायिक तर्क में प्रवेश नहीं करता।

यह गहराई-रक्षा की पहली रक्षा पंक्ति है, प्रभावी रूप से रोकती है:
- TRACE क्रॉस-साइट ट्रैकिंग आक्रमण (XST)
- CONNECT टनल प्रॉक्सी दुरुपयोग
- गैर-मानक WebDAV विधि प्रोबिंग
- स्वचालित स्कैनर की HTTP विधि गणना

### 2.1 XSS क्रॉस-साइट स्क्रिप्टिंग

सभी रेगुलर एक्सप्रेशन `SecurityFilter::PATTERNS['XSS']` से आते हैं, केस-असंवेदनशील मिलान।

| पहचान पैटर्न | रेगुलर एक्सप्रेशन | रक्षा किया जाने वाला आक्रमण |
|----------|------|-----------|
| स्क्रिप्ट टैग | `<\s*\/?\s*s\s*c\s*r\s*i\s*p\s*t\b` | `<script>`, `<script >`, `< script>` जैसे स्पेस-युक्त रूपांतर |
| इवेंट एट्रिब्यूट | `\bon\w+\s*=\s*[\"\']?\s*(?:javascript\|vbscript):` | `onclick="javascript:..."` जैसे इनलाइन इवेंट |
| JS छद्म प्रोटोकॉल | `(?:javascript\|vbscript)\s*:\s*(?:[^\s]*\s*)?(?:eval\|alert\|prompt\|confirm\|document\.cookie\|location\s*=)` | `javascript:eval(...)`, `javascript:alert(1)` आदि |
| Data URI XSS | `data\s*:\s*text\s*\/\s*html\s*(?:;base64)?\s*,` | `data:text/html,<script>`, `data:text/html;base64,...` आदि |
| टेम्पलेट इंजेक्शन | `\{\{.*?\}\}` | `{{constructor}}`, `{{7*7}}` जैसे सर्वर/Angular/Vue टेम्पलेट इंजेक्शन |

### 2.2 SQL इंजेक्शन

| पहचान पैटर्न | रेगुलर एक्सप्रेशन | रक्षा किया जाने वाला आक्रमण |
|----------|------|-----------|
| UNION संयुक्त क्वेरी | `\bUNION\s+(?:ALL\s+)?SELECT\b` | `UNION SELECT`, `UNION ALL SELECT` डेटा निष्कर्षण |
| OR हमेशा-सत्य इंजेक्शन | `(?:[\"\']\s*OR\s+[\"\']?\s*\d+\s*=\s*\d+\|[\"\']\s*OR\s+[\"\']?1[\"\']?\s*=\s*[\"\']?1)` | `' OR 1=1--`, `" OR '1'='1'` |
| तालिका संरचना विनाश | `\b(?:DROP\|ALTER\|TRUNCATE)\s+(?:TABLE\|DATABASE\|INDEX\|VIEW)\b` | `DROP TABLE users`, `TRUNCATE TABLE logs` |
| स्टोरेड प्रोसीजर कॉल | `\b(?:xp_cmdshell\|sp_executesql\|sp_addsrvrolemember)\b` | MSSQL विस्तारित स्टोरेड प्रोसीजर कमांड निष्पादन |
| मेटाडेटा प्रोबिंग | `\b(?:INFORMATION_SCHEMA\|sys\.(?:tables\|columns\|databases)\|pg_class\|sqlite_master\|mysql\.(?:user\|db))\b` | MySQL/PG/SQLite/MSSQL डेटाबेस संरचना प्रोबिंग |
| टिप्पणी बाइपास | `(?:[\"\'])\s*(?:--\|#)\s*[\"\']?\s*(?:OR\|AND\|SELECT\|INSERT\|UPDATE\|DELETE\|DROP)` | `'-- OR SELECT`, `'# AND UPDATE` टिप्पणी बाइपास |

### 2.3 पाथ ट्रैवर्सल

| पहचान पैटर्न | रेगुलर एक्सप्रेशन | रक्षा किया जाने वाला आक्रमण |
|----------|------|-----------|
| निर्देशिका बैकट्रैक | `\.\.[\/\\\\]{2,}` | `../`, `..\`, `....//` बहु-स्तरीय निर्देशिका बैकट्रैक |
| संवेदनशील फ़ाइल प्रोबिंग | `\/(?:etc\/(?:passwd\|shadow\|hosts)\|proc\/self\|boot\.ini\|win\.ini\|WEB-INF\|\.env\|\.git\/)` | `/etc/passwd`, `/proc/self/environ`, `.env`, `.git/HEAD` आदि |
| नल बाइट ट्रंकेशन | `%00` | `../../../etc/passwd%00.jpg` एक्सटेंशन सत्यापन बाइपास |

### 2.4 कमांड इंजेक्शन

| पहचान पैटर्न | रेगुलर एक्सप्रेशन | रक्षा किया जाने वाला आक्रमण |
|----------|------|-----------|
| पाइप/सेमीकोलन कमांड | `[;\|&]\s*(?:ls\|cat\|rm\|wget\|curl\|nc\|bash\|sh\|cmd\|powershell\|python\|perl)\b` | `;cat /etc/passwd`, `\|bash` |
| बैकटिक प्रतिस्थापन | `` `[^`]*\b(?:cat\|ls\|id\|whoami\|pwd\|rm\|wget\|curl)\b[^`]*` `` | `` `cat /etc/passwd` `` |
| $() प्रतिस्थापन | `\$\(\s*(?:cat\|ls\|id\|whoami\|rm\|wget\|curl)\b` | `$(whoami)`, `$(cat flag)` |
| दूरस्थ डाउनलोड पाइप | `(?:wget\|curl)\s+.*(?:\b-o\b\|\b-O\b\|pipe\|bash\|python).*\bhttps?:\/\/` | `wget URL -O - \| bash`, `curl URL \| python` |

### 2.5 CSRF क्रॉस-साइट अनुरोध फोर्जरी

सत्यापन तर्क `SecurityFilter::checkCsrf()` में लागू:

```php
// 仅 POST/PUT/DELETE 触发校验
// Origin 头和 Referer 均为空 → 放行（非浏览器客户端）
// Origin 非空 → 解析 Origin 域名与 Host 比对
```

तुलना नियम:
- Host के `www.` उपसर्ग हटाकर Origin के डोमेन से सटीक तुलना
- Host, Origin का मूल डोमेन हो (जैसे `Origin: app.example.com`, `Host: example.com` — `str_contains($originHost, '.' . $hostOnly)` ट्रिगर), तो पास
- न सटीक मिलान, न सबडोमेन → 403, CSRF आक्रमण माना जाता है

ध्यान दें: गैर-ब्राउज़र क्लाइंट (जैसे curl बिना Origin/Referer) सीधे पास होते हैं, CSRF सुरक्षा केवल ब्राउज़र वातावरण के लिए प्रभावी है।

### 2.6 दुर्भावनापूर्ण फ़ाइल अपलोड

| पहचान पैटर्न | रेगुलर एक्सप्रेशन | रक्षा किया जाने वाला आक्रमण |
|----------|------|-----------|
| दोहरा एक्सटेंशन छद्म | `\.(?:php\d?\|phtml\|phar\|cgi\|pl\|py\|jsp\|asp)x?\.(?:png\|jpg\|gif\|pdf)` | `shell.php.png`, `shell.phar.jpg` व्हाइटलिस्ट बाइपास |
| PHP एक्सटेंशन | `\.php\s*$/m` | अनुरोध पैरामीटर में सीधे `.php` पथ |

## 3. आक्रमण एस्केलेशन और IP ब्लैकलिस्ट

SecurityFilter में अंतर्निहित आक्रमण एस्केलेशन तंत्र है, समान IP के लगातार स्कैनिंग आक्रमण रोकता है।

### एस्केलेशन प्रवाह

```
第 1 次扫描命中 → Redis INCR security_escalate:{ip} = 1, TTL=60s
第 2 次扫描命中 → INCR → 2
...
第 5 次扫描命中 → INCR → 5
    → 触发封禁: SETEX security_ban:{ip} 900 1
    → 清除计数器 DEL security_escalate:{ip}
    → 写入安全日志: [SECURITY] IP banned 15min
```

### प्रतिबंध अवधि व्यवहार

प्रत्येक अनुरोध SecurityFilter में प्रवेश करते समय पहले `isBanned()` जांचता है:

```php
if (Redis::get("security_ban:{$ip}")) {
    return response('<h1>403 Forbidden</h1>', 403);
}
```

प्रतिबंधित IP के सभी अनुरोध (वैध अनुरोध सहित) 15 मिनट तक सीधे 403 लौटते हैं, आगे के व्यावसायिक तर्क पूरी तरह छोड़ दिए जाते हैं।

### कॉन्फ़िगरेशन स्थिरांक

| स्थिरांक | मान | अर्थ |
|------|-----|------|
| ESCALATE_LIMIT | 5 | 60 सेकंड विंडो में ट्रिगर थ्रेशोल्ड संख्या |
| ESCALATE_WINDOW | 60 | काउंटर विंडो (सेकंड) |
| BAN_DURATION | 900 | ब्लैकलिस्ट अवधि (सेकंड), यानी 15 मिनट |

### सुरक्षा लॉग

फ़ाइल स्थान: `runtime/logs/security.log`

लॉग प्रारूप उदाहरण:
```
2026-05-20 14:32:11 [SECURITY] XSS attack blocked | IP: 192.168.1.100 | Path: /admin/user | Field: body.username | Source: body | Payload: <script>alert(1)</script>
2026-05-20 14:32:15 [SECURITY] IP banned 15min | IP: 192.168.1.100 | Triggers: 5
```

### अनुरोध निकाय आकार सीमा

`Content-Length > 10MB` सीधे 413 Payload Too Large लौटाता है, DoS विशाल अनुरोध निकाय आक्रमण रोकता है।

### Content-Type सत्यापन

POST/PUT अनुरोधों में **अनिवार्य** `Content-Type` `application/json` या `application/x-www-form-urlencoded` होना चाहिए, अन्यथा 415 Unsupported Media Type। फ़ाइल अपलोड अनुरोध (file फ़ील्ड सहित) इस जांच को छोड़ते हैं।

## 4. प्रतिक्रिया सुरक्षा हेडर

सभी हेडर `Cors` मिडलवेयर में इंजेक्ट होते हैं, `$response->withHeaders()` से प्रत्येक प्रतिक्रिया में जुड़ते हैं।

| हेडर | मान | कार्य |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | किसी भी स्रोत के क्रॉस-ओरिजिन की अनुमति (इंट्रानेट एडमिन बैकएंड परिदृश्य) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | अनुमत विधियों का समूह |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | अनुमत कस्टम हेडर |
| Access-Control-Max-Age | `86400` | प्रीफ़्लाइट अनुरोध कैश 24 घंटे |
| X-Content-Type-Options | `nosniff` | ब्राउज़र MIME स्निफिंग निषिद्ध |
| X-Frame-Options | `DENY` | सभी iframe एम्बेड निषिद्ध, क्लिकजैकिंग रोकथाम |
| X-XSS-Protection | `1; mode=block` | ब्राउज़र अंतर्निहित XSS फ़िल्टर सक्षम और पेज रेंडर अवरोध |
| Referrer-Policy | `strict-origin-when-cross-origin` | समान स्रोत पर पूर्ण URL, क्रॉस-ओरिजिन पर केवल डोमेन |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | पूरी साइट पर कैमरा/माइक्रोफ़ोन/लोकेशन API निषिद्ध |

OPTIONS प्रीफ़्लाइट अनुरोध सीधे 204 खाली प्रतिक्रिया लौटाता है, आगे की मिडलवेयर श्रृंखला में नहीं जाता।

### 4.2 Content-Security-Policy (CSP)

अन्य सुरक्षा हेडर के साथ Cors मिडलवेयर में इंजेक्ट होता है, गहराई-रक्षा प्रदान करता है, ब्राउज़र द्वारा लोड और निष्पादित होने वाले संसाधन स्रोत सीमित करता है।

| हेडर | मान | कार्य |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | स्क्रिप्ट/स्टाइल/छवि/कनेक्शन/फ्रेम/फ़ॉर्म आदि संसाधन स्रोत सीमित करता है |
| X-Permitted-Cross-Domain-Policies | `none` | Adobe Flash/PDF जैसी क्रॉस-डोमेन नीति फ़ाइल लोड निषिद्ध |

CSP नीति बिंदु:
- `default-src 'self'`: डिफ़ॉल्ट रूप से केवल समान-स्रोत संसाधन
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: समान-स्रोत स्क्रिप्ट + इनलाइन स्क्रिप्ट (Flutter Web अनिवार्य) + eval (Flutter Web डिबग अनिवार्य)
- `frame-ancestors 'none'`: किसी भी पेज में iframe एम्बेड निषिद्ध, X-Frame-Options: DENY के साथ दोहरी सुरक्षा
- `base-uri 'self'`: `<base>` टैग केवल समान-स्रोत की ओर
- `form-action 'self'`: फ़ॉर्म केवल समान-स्रोत में सबमिट

## 5. दर सीमा नीति

### एल्गोरिदम

Redis Sorted Set स्लाइडिंग विंडो + Lua एटॉमिक स्क्रिप्ट, मुख्य संचालन:

```lua
-- 1. 清理窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. 检查当前窗口计数
local count = redis.call('ZCARD', KEYS[1])
-- 3. 超限则返回 {0, count}，未超限则 ZADD 并返回 {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- 随机后缀避免同毫秒覆盖
redis.call('EXPIRE', KEYS[1], window + 10)
```

Lua स्क्रिप्ट Redis सर्वर पर सिंगल-थ्रेड निष्पादित होती है, **स्वाभाविक रूप से एटॉमिक**, TOCTOU (Time-of-check to Time-of-use) रेस स्थिति समाप्त करती है।

### दर सीमा कॉन्फ़िगरेशन

| रूट | सीमा | विंडो | परिदृश्य |
|------|------|------|------|
| डिफ़ॉल्ट (सभी रूट) | 60 बार/मिनट | 60s | सामान्य API |
| `/api/auth/login` | 10 बार/मिनट | 60s | लॉगिन (ब्रूट-फोर्स रोकथाम) |
| `/api/auth/register` | 5 बार/मिनट | 60s | पंजीकरण (बैच पंजीकरण रोकथाम) |

### प्रतिक्रिया हेडर

दर सीमा ट्रिगर पर HTTP 429 और JSON body लौटता है:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

सभी प्रतिक्रियाओं (सामान्य सहित) में निम्न हेडर होते हैं:

| हेडर | विवरण |
|----|------|
| X-RateLimit-Limit | वर्तमान विंडो में अधिकतम अनुमत अनुरोध संख्या |
| X-RateLimit-Remaining | वर्तमान विंडो में शेष अनुरोध संख्या |
| X-RateLimit-Reset | विंडो रीसेट का Unix टाइमस्टैम्प |
| Retry-After | केवल दर सीमा पर, अनुशंसित प्रतीक्षा सेकंड |

### डिग्रेडेशन नीति

Redis असामान्य (कनेक्शन टाइमआउट, अनुपलब्ध आदि) पर **fail-closed**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    // Redis down: 限流不可用即拒绝，避免安全防线失效（登录/支付回调限流为空转）
    return json(['code' => 503, 'message' => '服务暂不可用，请稍后再试', 'data' => []])
        ->withStatus(503)->withHeaders(['Retry-After' => '5']);
}
```

दर सीमा लॉगिन ब्रूट-फोर्स रोकथाम और पेमेंट कॉलबैक रीप्ले रोकथाम की पहली सुरक्षा रेखा है, Redis विफलता पर अनुरोध अस्वीकार करना (503) बेहतर है, पास करना नहीं।

### 5.4 खाता लॉक तंत्र

लॉगिन इंटरफ़ेस दर सीमा के आधार पर अतिरिक्त **खाता लॉक** तंत्र जोड़ता है, किसी विशेष उपयोगकर्ता के लक्षित ब्रूट-फोर्स को रोकता है।

**लॉक प्रवाह**:

```
登录失败 → Redis INCR account_lockout:{userId} TTL=900s
连续 5 次失败 → Redis SETEX account_locked:{userId} 900 1
            → 返回 429 "账号已被锁定，请15分钟后再试"
            → 清除计数器 DEL account_lockout:{userId}
```

**लॉक अवधि व्यवहार**:

लॉक अवधि में सभी लॉगिन अनुरोध सीधे 429 लौटते हैं, पासवर्ड सत्यापन नहीं होता, ब्रूट-फोर्स प्रयास पूरी तरह रुकते हैं।

**कॉन्फ़िगरेशन स्थिरांक**:

| स्थिरांक | मान | अर्थ |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | अधिकतम लगातार विफल संख्या |
| LOCKOUT_DURATION | 900 | लॉक अवधि (सेकंड), यानी 15 मिनट |

ध्यान दें: खाता लॉक `userId` पर आधारित है, IP पर नहीं, इसलिए आक्रमणकारी IP बदलकर लॉक बाइपास नहीं कर सकता। IP दर सीमा (10 बार/मिनट) के साथ मिलकर दोहरी सुरक्षा बनती है:
- IP स्तर: 10 बार/मिनट दर सीमा वितरित ब्रूट-फोर्स रोकती है
- खाता स्तर: 5 विफलताओं पर लॉक लक्षित ब्रूट-फोर्स रोकता है

## 6. प्रमाणीकरण और प्राधिकरण

### 6.1 JWT प्रमाणीकरण

AdminAuth मिडलवेयर लागू करता है, प्रमाणीकरण आवश्यक रूट समूह पर माउंट।

**पैरामीटर कॉन्फ़िगरेशन** (`config/plugin/erikwang2013/jwt/jwt`, `.env` से इंजेक्ट):

| पैरामीटर | मान | विवरण |
|------|-----|------|
| एल्गोरिदम | HS256 | HMAC-SHA256 सममित सिग्नेचर |
| कुंजी | `JWT_SECRET_KEY` | पर्यावरण चर इंजेक्शन, अनुपस्थित या डिफ़ॉल्ट मान पर **स्टार्टअप अस्वीकार** (fail-closed) |
| access_token TTL | 7200s (2h) | `JWT_TTL` |
| refresh_token TTL | 1209600s (14d) | `JWT_REFRESH_TTL` |
| जारीकर्ता | `open-admin` | `JWT_ISSUER` |
| श्रोता | `open-admin` | `JWT_AUDIENCE` |

**Token निष्कर्षण**: `Authorization: Bearer <token>` हेडर से, `Bearer ` उपसर्ग हटाकर मूल JWT प्राप्त करें।

**प्रमाणीकरण प्रवाह**:
1. खाली token → सीधे 401 `{"code": 401, "message": "未登录"}`
2. Redis ब्लैकलिस्ट `jwt_blacklist:{md5(token)}` जांचें → हिट → 401 `Token已失效，请重新登录`
3. JWT decode → विफल (समाप्त/सिग्नेचर मेल नहीं) → 401 `Token已过期或无效`
4. सफल → `$request->adminId` और `$request->adminUsername` इंजेक्ट

**ब्लैकलिस्ट तंत्र**: उपयोगकर्ता लॉगआउट पर `md5(token)` Redis में लिखा जाता है, TTL = JWT शेष वैधता। Redis विफलता पर ब्लैकलिस्ट जांच छोड़ी जाती है (fail-open), तब लॉगआउट किए गए Token थोड़े समय उपयोग हो सकते हैं, लेकिन JWT की अल्पकालिक वैधता (2h) बैकअप सुरक्षा है।

**Token रीफ़्रेश**: `POST /api/auth/refresh` मूल refresh token (`token_type=refresh` और समाप्त नहीं/ब्लैकलिस्ट नहीं) सत्यापित करने के बाद ही नया जारी करता है, और `sub` वैध उपयोगकर्ता ID होना चाहिए — **sub=null वाला refresh token अब जारी नहीं होता**, रीफ़्रेश विफल पर सीधे 401।

### 6.2 समवर्ती सत्र सीमा

Token लीक के बाद मल्टी-डिवाइस दुरुपयोग रोकने के लिए, सिस्टम एक उपयोगकर्ता के एक साथ धारित वैध Token की संख्या सीमित करता है।

**सीमा तर्क**:

```
登录成功 → 签发新 Token
         → 查询当前用户有效 Token 数量: Redis SCARD user_tokens:{userId}
         → 若数量 >= 3（MAX_CONCURRENT_SESSIONS）:
            → 按创建时间升序排列，移除最旧的 Token:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → 将新 Token 加入集合: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**कॉन्फ़िगरेशन स्थिरांक**:

| स्थिरांक | मान | अर्थ |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | एक उपयोगकर्ता के अधिकतम समवर्ती Token संख्या |

**बाहर निकाले जाने का परिदृश्य**: जब उपयोगकर्ता चौथे डिवाइस पर लॉगिन करता है, पहले डिवाइस का Token बलपूर्वक ब्लैकलिस्ट होता है, आगे के अनुरोध 401 "Token已失效，请重新登录" लौटाते हैं।

लॉगआउट पर वर्तमान Token समूह से हटता है। Token स्वाभाविक रूप से समाप्त होने पर Redis key स्वतः अमान्य होती है, समूह सदस्य घटते हैं।

### 6.3 RBAC अनुमति मॉडल

AdminPermission मिडलवेयर लागू।

**डेटा मॉडल**: User -> Role -> Permission तीन-परत संबंध

- `erik_admin_user` (उपयोगकर्ता तालिका)
- `erik_admin_user_role` (उपयोगकर्ता-भूमिका संबंध तालिका)
- `erik_admin_role` (भूमिका तालिका)
- `erik_admin_role_permission` (भूमिका-अनुमति संबंध तालिका)
- `erik_admin_permission` (अनुमति तालिका)

**अनुमति प्रकार**:
| type | अर्थ | उदाहरण |
|------|------|------|
| 1 | मेनू अनुमति | बाएँ नेविगेशन की दृश्यता नियंत्रित करता है |
| 2 | बटन अनुमति | पेज के ऑपरेशन बटन नियंत्रित करता है (नया/संपादन/हटाना) |
| 3 | API अनुमति | बैकएंड इंटरफ़ेस कॉल नियंत्रित करता है |

API अनुमति पहचान प्रारूप: `{method}.{path}`

उदाहरण:
- `post.admin/user` — उपयोगकर्ता बनाना
- `put.admin/user` — उपयोगकर्ता संपादन
- `delete.admin/user` — उपयोगकर्ता हटाना
- `get.admin/user` — उपयोगकर्ता सूची देखना

**प्रमाणीकरण प्रवाह**:
1. `$request->adminId` खाली (लॉगिन नहीं) → सीधे 401 `{"code": 401, "message": "未登录"}`, आगे पास नहीं
2. उपयोगकर्ता → भूमिकाएँ (`status=0` अक्षम भूमिकाएँ छोड़कर) → अनुमति सूची प्राप्त करें
3. सुपर एडमिन (`slug = '*'`) → सीधे पास
4. `strtolower(method) . '.' . trim(path, '/')` बनाएं → अनुमति सूची से तुलना
5. मिलान विफल → 403 `{"code": 403, "message": "无权限访问"}`

**द्वितीय पुष्टि**: BaseController `confirmPassword()` विधि प्रदान करता है, संवेदनशील ऑपरेशन (उपयोगकर्ता हटाना, डेटा निर्यात आदि) में Controller परत पर वर्तमान पासवर्ड देना अतिरिक्त आवश्यक, सत्र अपहरण के बाद अनधिकृत ऑपरेशन रोकता है।

### 6.4 भुगतान कॉलबैक सिग्नेचर सत्यापन (fail-closed)

`POST /api/payment/callback` (Stripe/PayPal टॉप-अप कॉलबैक) सिग्नेचर सत्यापन **fail-closed** है, किसी भी कॉन्फ़िगरेशन की कमी या सत्यापन असामान्यता पर कॉलबैक अस्वीकार:

| परिदृश्य | व्यवहार |
|------|------|
| Stripe में `STRIPE_WEBHOOK_SECRET` कॉन्फ़िगर नहीं | अस्वीकार (403), बिना सिग्नेचर कॉलबैक स्वीकार नहीं |
| Stripe सिग्नेचर अनुपस्थित / सत्यापन विफल | अस्वीकार (403) |
| Stripe टाइमस्टैम्प `t=` अनुपस्थित या सर्वर समय से अंतर **> ±5 मिनट** | अस्वीकार (403), रीप्ले रोकथाम |
| PayPal में `PAYPAL_WEBHOOK_ID` कॉन्फ़िगर नहीं | अस्वीकार (403) |
| PayPal पुनः-सत्यापन असामान्य / SUCCESS नहीं | अस्वीकार (403) |
| वैकल्पिक `CALLBACK_TRUSTED_IPS` कॉन्फ़िगर होने पर स्रोत IP व्हाइटलिस्ट में नहीं | अस्वीकार (403) |
| कॉलबैक provider ऑर्डर भुगतान विधि से मेल नहीं / भुगतान विधि मौजूद नहीं | अस्वीकार (403) |

कॉलबैक क्रेडिट (स्थिति अपडेट + शेष + लेनदेन) एक ही डेटाबेस ट्रांज़ैक्शन में पूरा होता है, किसी भी चरण की विफलता पर पूर्ण रोलबैक, आधा-क्रेडिट रोकता है।

## 8. डेटा सुरक्षा

सिस्टम तीन-परत डेटा सुरक्षा नीति अपनाता है, डेटा प्रवाह के तीन चरणों के अनुरूप।

### 8.1 ट्रांसमिशन परत — EncryptionService

`EncryptionService` `erikwang2013/encryption` पैकेज का उपयोग करता है, API अनुरोध/प्रतिक्रिया के संवेदनशील फ़ील्ड एन्क्रिप्ट/डिक्रिप्ट करता है।

**तकनीकी विवरण**:
- एल्गोरिदम: `aes-256-cbc-hmac` (अंतर्निहित HMAC सिग्नेचर टैम्पर रोकथाम)
- कुंजी: `ENCRYPTION_KEY` पर्यावरण चर, स्वचालित रूप से 32 बाइट संरेखित
- उपयोग: क्लाइंट और API के बीच फ़ोन नंबर, ID कार्ड नंबर आदि फ़ील्ड ट्रांसमिशन

**मास्किंग उपकरण विधियाँ**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (उपयोगकर्ता नाम 2 अक्षर से अधिक) या `a**@example.com`

### 8.2 स्टोरेज परत — Encryptable Cast

`AdminUser` मॉडल `Erikwang2013\Encryptable\Encryptable` Eloquent cast उपयोग करता है, संबंधित फ़ील्ड:

- `email` → Encryptable cast, स्वचालित एन्क्रिप्शन/डिक्रिप्शन
- `phone` → Encryptable cast, स्वचालित एन्क्रिप्शन/डिक्रिप्शन
- `id_card` → Encryptable cast, स्वचालित एन्क्रिप्शन/डिक्रिप्शन

डेटाबेस में लिखते समय स्वचालित रूप से साइफरटेक्स्ट एन्क्रिप्ट होता है, पढ़ते समय स्वचालित रूप से प्लेनटेक्स्ट डिक्रिप्ट। डेटाबेस स्टोरेज कॉलम प्रकार `VARCHAR(500)` है, साइफरटेक्स्ट base64 रूप में संग्रहीत।

**कुंजी प्रणाली**: ट्रांसमिशन परत एन्क्रिप्शन (`ENCRYPTION_KEY`) से स्वतंत्र `ENCRYPTABLE_KEY` उपयोग, एक कुंजी का लीक दूसरी परत को अमान्य नहीं करता।

कुंजी रोटेशन: `ENCRYPTION_PREVIOUS_KEYS` पर्यावरण चर ऐतिहासिक कुंजी सूची (कॉमा-पृथक) समर्थित, पुराना डेटा पढ़ते समय ऐतिहासिक कुंजी से डिक्रिप्ट का प्रयास, लिखते समय वर्तमान कुंजी से पुनः एन्क्रिप्ट।

### 8.3 प्रदर्शन परत — ID अस्पष्टीकरण और मास्किंग

**Hashids ID अस्पष्टीकरण**: `HashidsService` `erikwang2013/hashids` पैकेज उपयोग करता है।

- बाह्य API द्वारा लौटाया गया डेटाबेस BIGINT ID hash स्ट्रिंग में एन्कोड (जैसे `xK3mN9qR2pL7wV8b`)
- क्लाइंट अनुरोध में hash स्ट्रिंग भेजता है, बैकएंड स्वचालित रूप से मूल ID डिकोड करता है
- सॉल्ट `HASHIDS_SALT` पर्यावरण चर इंजेक्शन, सॉल्ट अलग होने पर एन्कोड/डिकोड परिणाम पूरी तरह अलग
- hash न्यूनतम लंबाई 16 अक्षर, 62-अक्षर अल्फ़ान्यूमेरिक सेट
- BaseController `encodeId()`, `decodeId()`, `encodeIds()` सुविधाजनक विधियाँ प्रदान करता है

**निर्यात मास्किंग**: Excel/PDF निर्यात में (ExportController), संवेदनशील फ़ील्ड समान रूप से मास्क:
- फ़ोन नंबर: `138****1234`
- ईमेल: `a***@example.com`
- ID कार्ड: पूर्ण रूप से `********`

## 9. कुंजी प्रबंधन

सभी कुंजियाँ `.env` पर्यावरण चर से इंजेक्ट होती हैं, कॉन्फ़िगरेशन फ़ाइलें `getenv()` पढ़ती हैं और अंतर्निहित फ़ॉलबैक डिफ़ॉल्ट मान रखती हैं (केवल विकास वातावरण के लिए सुरक्षित)।

| पर्यावरण चर | उपयोग | पैकेज | प्रोडक्शन आवश्यकता |
|----------|------|-----|---------|
| JWT_SECRET_KEY | JWT सिग्नेचर कुंजी | erikwang2013/jwt-webman | 64+ अक्षर यादृच्छिक स्ट्रिंग; अनुपस्थित या डिफ़ॉल्ट मान पर स्टार्टअप अस्वीकार |
| JWT_ALGORITHM | JWT सिग्नेचर एल्गोरिदम | वही | HS256 रखें |
| HASHIDS_SALT | ID एन्कोडिंग सॉल्ट | erikwang2013/hashids | यादृच्छिक स्ट्रिंग |
| SNOWFLAKE_DATACENTER_ID | डेटासेंटर ID (0-31) | erikwang2013/snowflake-php | एकल डेटासेंटर में डिफ़ॉल्ट रखें |
| ENCRYPTION_KEY | API ट्रांसमिशन परत एन्क्रिप्शन कुंजी | erikwang2013/encryption | 32 बाइट यादृच्छिक स्ट्रिंग |
| ENCRYPTABLE_KEY | DB स्टोरेज परत एन्क्रिप्शन कुंजी | erikwang2013/encryptable | 32 बाइट यादृच्छिक स्ट्रिंग, ट्रांसमिशन कुंजी से भिन्न |

**सुरक्षा आवश्यकताएँ**:
- `.env` फ़ाइल `.gitignore` में है, वर्ज़न रिपॉज़िटरी में कमिट सख्त निषिद्ध
- `.env.example` सार्वजनिक टेम्पलेट फ़ाइल है, वास्तविक कुंजियाँ नहीं रखती
- प्रोडक्शन में **अनिवार्य** सभी डिफ़ॉल्ट कुंजियाँ यादृच्छिक स्ट्रिंग में बदलें
- कुंजी उत्पन्न करने के लिए `openssl rand -base64 32` अनुशंसित

## 10. security.txt (RFC 9116)

सिस्टम `/.well-known/security.txt` पर RFC 9116 मानक अनुसार सुरक्षा संपर्क जानकारी एंडपॉइंट प्रदान करता है, सुरक्षा शोधकर्ताओं को कमज़ोरी मिलने पर तुरंत रिपोर्ट चैनल ढूंढने में सहायता करता है।

**पहुंच विधि**:

```
GET /.well-known/security.txt
```

**प्रतिक्रिया सामग्री**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**फ़ील्ड विवरण**:

| फ़ील्ड | विवरण |
|------|------|
| Contact | सुरक्षा कमज़ोरी रिपोर्ट संपर्क |
| Expires | फ़ाइल समाप्ति समय, नियमित अद्यतन आवश्यक |
| Preferred-Languages | पसंदीदा संचार भाषा |
| Canonical | इस फ़ाइल का मानक URL |
| Policy | सुरक्षा नीति/कमज़ोरी प्रकटीकरण नीति लिंक |

यह एंडपॉइंट दर सीमा, प्रमाणीकरण जैसे मिडलवेयर से सीमित नहीं, कोई भी सीधे पहुंच सकता है।

## 11. Nginx सुरक्षा कॉन्फ़िगरेशन

प्रोजेक्ट `docs/nginx-security.conf` प्रोडक्शन वातावरण Nginx रिवर्स प्रॉक्सी के सुरक्षा हार्डनिंग संदर्भ कॉन्फ़िगरेशन के रूप में प्रदान करता है।

**शामिल सुरक्षा उपाय**:

| कॉन्फ़िगरेशन आइटम | कार्य |
|--------|------|
| `server_tokens off` | Nginx संस्करण संख्या छिपाता है |
| `client_max_body_size 10m` | अनुरोध निकाय आकार सीमित करता है, SecurityFilter के साथ समन्वय |
| `limit_req_zone` | Nginx स्तर पर अनुरोध आवृत्ति सीमा |
| `limit_conn_zone` | समवर्ती कनेक्शन संख्या सीमा |
| `add_header` सुरक्षा हेडर | Nginx स्तर पर X-XSS-Protection जैसे सुरक्षा हेडर जोड़ना |
| `if ($request_method)` | Nginx स्तर पर गैर-मानक HTTP विधि अस्वीकार |
| SSL/TLS कॉन्फ़िगरेशन | आधुनिक TLS 1.2/1.3 कॉन्फ़िगरेशन, कमज़ोर साइफर सूट अक्षम |
| बैकएंड हेडर छिपाना | `proxy_hide_header` webman संस्करण जैसे संवेदनशील हेडर हटाता है |

**उपयोग विधि**: `docs/nginx-security.conf` के कॉन्फ़िगरेशन को अपने Nginx server ब्लॉक में मर्ज करें, वास्तविक डोमेन और प्रमाणपत्र पथ के अनुसार समायोजित करें।

## 12. खतरा मॉडल

### 12.1 संरक्षित खतरे

| खतरा प्रकार | आक्रमण वेक्टर | रक्षा परतें |
|----------|---------|---------|
| HTTP विधि दुरुपयोग | TRACE/TRACK XST आक्रमण, CONNECT टनल प्रॉक्सी, WebDAV विधि प्रोबिंग | SecurityFilter 405 विधि व्हाइटलिस्ट (GET/POST/PUT/DELETE/OPTIONS/HEAD) |
| लक्षित ब्रूट-फोर्स | विशेष उपयोगकर्ता के लिए बार-बार पासवर्ड प्रयास | खाता लॉक (5 विफलता पर 15 मिनट लॉक) + RateLimit (लॉगिन 10/मिनट) + Captcha |
| ब्रूट-फोर्स | वितरित IP से बार-बार उपयोगकर्ता नाम/पासवर्ड प्रयास | RateLimit (लॉगिन 10/मिनट) + Captcha |
| XSS क्रॉस-साइट स्क्रिप्टिंग | `<script>`, onerror, javascript: | SecurityFilter (5 पैटर्न) + X-XSS-Protection प्रतिक्रिया हेडर + CSP |
| SQL इंजेक्शन | UNION SELECT, OR 1=1, टिप्पणी बाइपास | SecurityFilter (6 पैटर्न) + Eloquent ORM पैरामीटराइज़्ड क्वेरी |
| CSRF क्रॉस-साइट अनुरोध फोर्जरी | दुर्भावनापूर्ण साइट द्वारा अनुरोध भेजना | SecurityFilter Origin/Referer सत्यापन |
| पाथ ट्रैवर्सल | `../../etc/passwd` | SecurityFilter पाथ ट्रैवर्सल पैटर्न + UploadController एक्सटेंशन व्हाइटलिस्ट |
| कमांड इंजेक्शन | `;ls`, `` `whoami` ``, `$(cat ...)` | SecurityFilter (4 पैटर्न) |
| सत्र अपहरण | JWT Token चोरी | JWT अल्पकालिक वैधता (2h) + ब्लैकलिस्ट लॉगआउट + संवेदनशील ऑपरेशन द्वितीय पासवर्ड पुष्टि |
| ID गणना | संख्यात्मक ID ट्रैवर्स कर डेटा मात्रा अनुमान | Hashids यादृच्छिक स्ट्रिंग अस्पष्टीकरण |
| डेटा लीक | DB डंप / मिडलमैन / लॉग लीक | तीन-परत एन्क्रिप्शन/मास्किंग + OperationLog संवेदनशील फ़ील्ड फ़िल्टर |
| DoS आक्रमण | विशाल अनुरोध निकाय / उच्च आवृत्ति अनुरोध | अनुरोध निकाय 10MB सीमा + RateLimit 60/मिनट + IP ब्लैकलिस्ट |
| अनुमति वृद्धि | कम अनुमति उपयोगकर्ता एडमिन इंटरफ़ेस तक पहुंच | RBAC method.path ग्रैन्युलैरिटी प्रमाणीकरण |
| फ़ाइल अपलोड आक्रमण | shell.php.png दोहरा एक्सटेंशन | SecurityFilter दुर्भावनापूर्ण फ़ाइल पहचान |

### 12.2 ज्ञात सीमाएँ

| सीमा | प्रभाव क्षेत्र | शमन उपाय |
|------|---------|---------|
| CSRF सुरक्षा केवल ब्राउज़र के लिए | गैर-ब्राउज़र क्लाइंट (curl, Postman, मोबाइल App) Origin/Referer जांच छोड़ सकते हैं | गैर-ब्राउज़र क्लाइंट स्वाभाविक रूप से CSRF आक्रमण से मुक्त; Cookie के बजाय JWT प्रमाणीकरण पर निर्भर |
| Redis अनुपलब्ध पर दर सीमा fail-closed (503), ब्लैकलिस्ट जांच fail-open | दर सीमा अवधि में कुछ अनुरोध अस्वीकार; लॉगआउट किए Token अल्पकाल उपयोग योग्य | Redis उपलब्धता मॉनिटरिंग अलर्ट; JWT अल्पकालिक वैधता बैकअप |
| कोई स्वतंत्र WAF इंजन नहीं | SecurityFilter `@preg_match` रेगुलर मिलान, समर्पित WAF नियम इंजन नहीं | प्रोडक्शन में Nginx ModSecurity या Cloudflare WAF आगे रखने की सलाह |
| JWT स्टेटलेस, सक्रिय रूप से अमान्य नहीं कर सकता | Token समाप्त होने से पहले सर्वर पक्ष से सक्रिय रूप से रद्द नहीं हो सकता (ब्लैकलिस्ट के अलावा) | ब्लैकलिस्ट + अल्पकालिक 2h TTL जोखिम विंडो कम करते हैं |
| IP ब्लैकलिस्ट केवल मेमोरी में | Redis रीस्टार्ट पर ब्लैकलिस्ट खो जाती है | Ban अवधि केवल 15 मिनट, प्रभाव सीमित |
| एडमिन एंडपॉइंट पर विशेष दर सीमा नहीं | एडमिन इंटरफ़ेस सामान्य इंटरफ़ेस के साथ 60/मिनट डिफ़ॉल्ट सीमा साझा करते हैं | एडमिन ऑपरेशन आवृत्ति स्वाभाविक रूप से कम, फ़िलहाल भेद आवश्यक नहीं |
| `@preg_match` त्रुटि दमन | विकृत रेगुलर इनपुट पर मौन विफल | `preg_last_error()` से मॉनिटरिंग जोड़ी जा सकती है, वर्तमान में लागू नहीं |
