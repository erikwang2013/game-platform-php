## 1. بانوراما الدفاع المتعمق

يعتمد النظام نموذج دفاع متعمق من 7 طبقات، من الخارج إلى الداخل تصفية الطلبات الخبيثة طبقة تلو الأخرى، لضمان أنه عند تعطل أي طبقة واحدة تبقى خطوط دفاع لاحقة تحمي النظام.

تُنفَّذ سلسلة الوسيطات كاملة بالترتيب التالي (راجع `config/middleware.php`):

```
الطلب → Cors → SecurityFilter → RateLimit → [وسيطات مجموعة المسارات: AdminAuth → AdminPermission → OperationLog] → Controller
```

| الطبقة | الوسيطة/الآلية | هدف الحماية |
|----|--------|---------|
| 1 | SecurityFilter | اعتراض هجمات XSS / حقن SQL / اجتياز المسار / حقن الأوامر / CSRF |
| 2 | Cors | أمان المشاركة عبر الأصول + حقن ترويسات الاستجابة الأمنية |
| 3 | RateLimit | نافذة منزلقة في Redis، تمنع التخمين العنيف |
| 4 | AdminAuth | مصادقة JWT + تسجيل خروج بالقائمة السوداء |
| 5 | AdminPermission | تحقق RBAC على مستوى method.path |
| 6 | OperationLog | تدقيق العمليات + تتبع طرف المصدر |
| 7 | تشفير البيانات | إخفاء معرفات Hashids + تشفير Encryptable لقاعدة البيانات + تشفير EncryptionService للنقل |

لدى الواجهة الأمامية (Flutter) ثلاث طبقات إضافية بتحقق مدخلات مستقل، ولا تثق الواجهة الخلفية بها، فكل طبقة تدافع بشكل مستقل.

## 2. محرك كشف الهجمات

### 2.0 تقييد طرق HTTP

يتحقق SecurityFilter أولاً من طريقة HTTP قبل جميع عمليات كشف الهجمات، ويسمح فقط بالطرق القياسية التالية:

```
GET, POST, PUT, DELETE, OPTIONS, HEAD
```

الطرق غير القياسية (مثل TRACE وCONNECT وPATCH والطرق المخصصة وغيرها) تُرجع مباشرة **405 Method Not Allowed**، وجسم الاستجابة HTML فارغ، دون الدخول في كشف الهجمات أو منطق الأعمال اللاحق.

هذا خط الدفاع الأول في الدفاع المتعمق، ويمنع بفعالية:
- هجمات التتبع عبر المواقع TRACE (XST)
- إساءة استخدام نفق CONNECT كوكيل
- فحص طرق WebDAV غير القياسية
- تعداد طرق HTTP عبر الماسحات الآلية

### 2.1 XSS البرمجة النصية عبر المواقع

جميع التعبيرات من `SecurityFilter::PATTERNS['XSS']`، مطابقة غير حساسة لحالة الأحرف.

| نمط الكشف | التعبير النمطي | الهجمات المُدافَع عنها |
|----------|------|-----------|
| وسوم السكربت | `<\s*\/?\s*s\s*c\s*r\s*i\s*p\s*t\b` | `<script>`, `<script >`, `< script>` وغيرها من المتغيرات ذات المسافات |
| خصائص الأحداث | `\bon\w+\s*=\s*[\"\']?\s*(?:javascript\|vbscript):` | `onclick="javascript:..."` وغيرها من الأحداث المضمنة |
| بروتوكول JS الزائف | `(?:javascript\|vbscript)\s*:\s*(?:[^\s]*\s*)?(?:eval\|alert\|prompt\|confirm\|document\.cookie\|location\s*=)` | `javascript:eval(...)`, `javascript:alert(1)` وغيرها |
| XSS عبر Data URI | `data\s*:\s*text\s*\/\s*html\s*(?:;base64)?\s*,` | `data:text/html,<script>`, `data:text/html;base64,...` وغيرها |
| حقن القوالب | `\{\{.*?\}\}` | `{{constructor}}`, `{{7*7}}` وغيرها من حقن قوالب الخادم/Angular/Vue |

### 2.2 حقن SQL

| نمط الكشف | التعبير النمطي | الهجمات المُدافَع عنها |
|----------|------|-----------|
| استعلام UNION | `\bUNION\s+(?:ALL\s+)?SELECT\b` | `UNION SELECT`, `UNION ALL SELECT` لتفريغ قواعد البيانات |
| حقن OR الصحيح دائمًا | `(?:[\"\']\s*OR\s+[\"\']?\s*\d+\s*=\s*\d+\|[\"\']\s*OR\s+[\"\']?1[\"\']?\s*=\s*[\"\']?1)` | `' OR 1=1--`, `" OR '1'='1'` |
| تدمير بنية الجداول | `\b(?:DROP\|ALTER\|TRUNCATE)\s+(?:TABLE\|DATABASE\|INDEX\|VIEW)\b` | `DROP TABLE users`, `TRUNCATE TABLE logs` |
| استدعاء الإجراءات المخزنة | `\b(?:xp_cmdshell\|sp_executesql\|sp_addsrvrolemember)\b` | تنفيذ أوامر عبر إجراءات MSSQL الموسعة |
| فحص البيانات الوصفية | `\b(?:INFORMATION_SCHEMA\|sys\.(?:tables\|columns\|databases)\|pg_class\|sqlite_master\|mysql\.(?:user\|db))\b` | فحص بنية قواعد MySQL/PG/SQLite/MSSQL |
| تجاوز بالتعليقات | `(?:[\"\'])\s*(?:--\|#)\s*[\"\']?\s*(?:OR\|AND\|SELECT\|INSERT\|UPDATE\|DELETE\|DROP)` | تجاوز بالتعليقات `'-- OR SELECT`, `'# AND UPDATE` |

### 2.3 اجتياز المسار

| نمط الكشف | التعبير النمطي | الهجمات المُدافَع عنها |
|----------|------|-----------|
| الرجوع للخلف في الدلائل | `\.\.[\/\\\\]{2,}` | `../`, `..\`, `....//` رجوع متعدد المستويات في الدلائل |
| فحص الملفات الحساسة | `\/(?:etc\/(?:passwd\|shadow\|hosts)\|proc\/self\|boot\.ini\|win\.ini\|WEB-INF\|\.env\|\.git\/)` | `/etc/passwd`, `/proc/self/environ`, `.env`, `.git/HEAD` وغيرها |
| القطع بالبايت الفارغ | `%00` | `../../../etc/passwd%00.jpg` لتجاوز فحص الامتدادات |

### 2.4 حقن الأوامر

| نمط الكشف | التعبير النمطي | الهجمات المُدافَع عنها |
|----------|------|-----------|
| أوامر بأنابيب/فواصل منقوطة | `[;\|&]\s*(?:ls\|cat\|rm\|wget\|curl\|nc\|bash\|sh\|cmd\|powershell\|python\|perl)\b` | `;cat /etc/passwd`, `\|bash` |
| استبدال بعلامات التنصيص الخلفية | `` `[^`]*\b(?:cat\|ls\|id\|whoami\|pwd\|rm\|wget\|curl)\b[^`]*` `` | `` `cat /etc/passwd` `` |
| استبدال $() | `\$\(\s*(?:cat\|ls\|id\|whoami\|rm\|wget\|curl)\b` | `$(whoami)`, `$(cat flag)` |
| تنزيل عن بعد بأنبوب | `(?:wget\|curl)\s+.*(?:\b-o\b\|\b-O\b\|pipe\|bash\|python).*\bhttps?:\/\/` | `wget URL -O - \| bash`, `curl URL \| python` |

### 2.5 CSRF تزوير الطلبات عبر المواقع

منطق التحقق منفَّذ في `SecurityFilter::checkCsrf()`:

```php
// التحقق يُطلق فقط لـ POST/PUT/DELETE
// عندما تكون ترويسة Origin وReferer فارغتين → تمرير (عملاء غير متصفحين)
// Origin غير فارغ → تحليل نطاق Origin ومقارنته مع Host
```

قواعد المقارنة:
- إزالة بادئة `www.` من Host ثم مقارنة دقيقة مع نطاق Origin
- إذا كان Host نطاقًا أبًا لـ Origin (مثل `Origin: app.example.com`, `Host: example.com` — يُطلق `str_contains($originHost, '.' . $hostOnly)`) → تمرير
- لا تطابق دقيق ولا نطاق فرعي → يُرجع 403 ويُحكم بأنها هجمة CSRF

ملاحظة: العملاء غير المتصفحين (مثل curl بدون Origin/Referer) يمررون مباشرة، وحماية CSRF فعّالة فقط في بيئة المتصفح.

### 2.6 رفع الملفات الخبيثة

| نمط الكشف | التعبير النمطي | الهجمات المُدافَع عنها |
|----------|------|-----------|
| تمويه بامتداد مزدوج | `\.(?:php\d?\|phtml\|phar\|cgi\|pl\|py\|jsp\|asp)x?\.(?:png\|jpg\|gif\|pdf)` | `shell.php.png`, `shell.phar.jpg` لتجاوز القائمة البيضاء |
| امتداد PHP | `\.php\s*$/m` | تمرير مسارات `.php` مباشرة في معاملات الطلب |

## 3. تصعيد الهجمات والقائمة السوداء للـ IP

يضمّن SecurityFilter آلية تصعيد الهجمات لمنع مسح هجومي مستمر من نفس الـ IP.

### تدفق التصعيد

```
الإصابة الأولى في الفحص → Redis INCR security_escalate:{ip} = 1, TTL=60s
الإصابة الثانية في الفحص → INCR → 2
...
الإصابة الخامسة في الفحص → INCR → 5
    → إطلاق الحظر: SETEX security_ban:{ip} 900 1
    → مسح العداد: DEL security_escalate:{ip}
    → كتابة سجل الأمان: [SECURITY] IP banned 15min
```

### السلوك خلال الحظر

عند دخول كل طلب إلى SecurityFilter يُفحص أولاً `isBanned()`:

```php
if (Redis::get("security_ban:{$ip}")) {
    return response('<h1>403 Forbidden</h1>', 403);
}
```

أثناء حظر الـ IP لمدة 15 دقيقة، تُرجع جميع الطلبات (بما فيها القانونية) 403 مباشرة، وتتجاوز منطق الأعمال اللاحق تمامًا.

### ثوابت التكوين

| الثابت | القيمة | المعنى |
|------|-----|------|
| ESCALATE_LIMIT | 5 | عتبة عدد الإصابات خلال نافذة 60 ثانية |
| ESCALATE_WINDOW | 60 | نافذة العداد (بالثواني) |
| BAN_DURATION | 900 | مدة القائمة السوداء (بالثواني)، أي 15 دقيقة |

### سجل الأمان

موقع الملف: `runtime/logs/security.log`

مثال على تنسيق السجل:
```
2026-05-20 14:32:11 [SECURITY] XSS attack blocked | IP: 192.168.1.100 | Path: /admin/user | Field: body.username | Source: body | Payload: <script>alert(1)</script>
2026-05-20 14:32:15 [SECURITY] IP banned 15min | IP: 192.168.1.100 | Triggers: 5
```

### حد حجم جسم الطلب

عند `Content-Length > 10MB` يُرجع مباشرة 413 Payload Too Large، لمنع هجمات DoS بأجسام طلبات ضخمة.

### التحقق من Content-Type

يجب أن يعلن طلب POST/PUT عن `Content-Type` كـ `application/json` أو `application/x-www-form-urlencoded`، وإلا يُرجع 415 Unsupported Media Type. طلبات رفع الملفات (ذات حقل file) تتجاوز هذا الفحص.

## 4. ترويسات الاستجابة الأمنية

تُحقن جميع الترويسات في وسيطة `Cors`، عبر `$response->withHeaders()` المُلحق بكل استجابة.

| الترويسة | القيمة | الوظيفة |
|----|-----|------|
| Access-Control-Allow-Origin | `*` | السماح بالعمل عبر الأصول من أي مصدر (سيناريو لوحة الإدارة داخل الشبكة) |
| Access-Control-Allow-Methods | `GET,POST,PUT,DELETE,OPTIONS` | مجموعة الطرق المسموح بها |
| Access-Control-Allow-Headers | `Authorization,Content-Type,API-Version` | الترويسات المخصصة المسموح بها |
| Access-Control-Max-Age | `86400` | تخزين طلبات الفحص المسبق 24 ساعة |
| X-Content-Type-Options | `nosniff` | منع المتصفح من فحص MIME |
| X-Frame-Options | `DENY` | منع التضمين في كل iframe، ضد اختطاف النقر |
| X-XSS-Protection | `1; mode=block` | تفعيل مرشح XSS المدمج في المتصفح واعتراض عرض الصفحة |
| Referrer-Policy | `strict-origin-when-cross-origin` | نفس الأصل يُرسل URL كاملًا، عبر الأصول يُرسل النطاق فقط |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | تعطيل واجهات الكاميرا/الميكروفون/الموقع في الموقع كله |

طلبات الفحص المسبق OPTIONS تُرجع مباشرة 204 بجسم فارغ، دون الدخول في سلسلة الوسيطات اللاحقة.

### 4.2 Content-Security-Policy (CSP)

تُحقن مع الترويسات الأمنية الأخرى في وسيطة Cors، لتوفير دفاع متعمق يقيد مصادر الموارد التي يمكن للمتصفح تحميلها وتنفيذها.

| الترويسة | القيمة | الوظيفة |
|----|-----|------|
| Content-Security-Policy | `default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` | تقييد مصادر السكربت/الأنماط/الصور/الاتصالات/الأطر/النماذج |
| X-Permitted-Cross-Domain-Policies | `none` | منع تحميل ملفات سياسات العمل عبر النطاقات في Adobe Flash/PDF وغيرها |

نقاط سياسة CSP الأساسية:
- `default-src 'self'`: افتراضيًا يسمح فقط بموارد نفس الأصل
- `script-src 'self' 'unsafe-inline' 'unsafe-eval'`: السماح بسكربتات نفس الأصل + السكربتات المضمنة (إلزامي لـ Flutter Web) + eval (إلزامي لتصحيح Flutter Web)
- `frame-ancestors 'none'`: منع التضمين في iframe من أي صفحة، ضمانة مزدوجة مع X-Frame-Options: DENY
- `base-uri 'self'`: تقييد وسم `<base>` على نفس الأصل فقط
- `form-action 'self'`: تقييد إرسال النماذج لنفس الأصل فقط

## 5. استراتيجية الحد من المعدل

### الخوارزمية

Redis Sorted Set نافذة منزلقة + نص Lua ذري، العمليات الأساسية:

```lua
-- 1. تنظيف السجلات القديمة خارج النافذة
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)
-- 2. فحص عدد النافذة الحالية
local count = redis.call('ZCARD', KEYS[1])
-- 3. عند تجاوز الحد يُرجع {0, count}، وإلا ZADD ويُرجع {1, count+1}
if count >= limit then return {0, count} end
redis.call('ZADD', KEYS[1], now, now . '.' . random)  -- لاحقة عشوائية لتجنب الكتابة فوق نفس المللي ثانية
redis.call('EXPIRE', KEYS[1], window + 10)
```

يُنفَّذ نص Lua في خيط واحد على خادم Redis، **ذرّي بطبيعته**، ما يزيل سباق TOCTOU (Time-of-check to Time-of-use).

### تكوين الحد من المعدل

| المسار | الحد | النافذة | السيناريو |
|------|------|------|------|
| الافتراضي (كل المسارات) | 60 مرة/دقيقة | 60s | API عام |
| `/api/auth/login` | 10 مرات/دقيقة | 60s | تسجيل الدخول (منع التخمين العنيف) |
| `/api/auth/register` | 5 مرات/دقيقة | 60s | التسجيل (منع التسجيل الجماعي) |

### ترويسات الاستجابة

عند تفعيل الحد من المعدل يُرجع HTTP 429 مع جسم JSON:
```json
{"code": 429, "message": "请求过于频繁，请稍后再试", "data": []}
```

تحمل جميع الاستجابات (بما فيها العادية) الترويسات التالية:

| الترويسة | الوصف |
|----|------|
| X-RateLimit-Limit | الحد الأقصى لعدد الطلبات في النافذة الحالية |
| X-RateLimit-Remaining | عدد الطلبات المتاحة المتبقية في النافذة الحالية |
| X-RateLimit-Reset | الطابع الزمني Unix لإعادة تعيين النافذة |
| Retry-After | تُحمل فقط عند تفعيل الحد، عدد الثواني المقترح للانتظار |

### استراتيجية التدهور

عند حدوث خلل في Redis (انتهاء مهلة الاتصال، عدم التوفر وغيرها) يكون الإغلاق آمنًا **fail-closed**:

```php
try {
    $result = Redis::eval($lua, ...);
} catch (\Throwable $e) {
    // Redis معطل: رفض الحد من المعدل أي رفض الطلبات، لتجنب انهيار خط الدفاع الأمني (حد تسجيل الدخول/رد الدفع يدور بلا فائدة)
    return json(['code' => 503, 'message' => '服务暂不可用，请稍后再试', 'data' => []])
        ->withStatus(503)->withHeaders(['Retry-After' => '5']);
}
```

الحد من المعدل هو خط الدفاع الأول ضد التخمين العنيف في تسجيل الدخول وإعادة تشغيل ردود الدفع؛ عند تعطل Redis يُفضَّل رفض الطلبات (503) على تمريرها.

### 5.4 آلية قفل الحساب

يضيف واجهة تسجيل الدخول، فوق الحد من المعدل، آلية **قفل الحساب** لمنع التخمين العنيف الموجه لمستخدم معين.

**تدفق القفل**:

```
فشل تسجيل الدخول → Redis INCR account_lockout:{userId} TTL=900s
5 حالات فشل متتالية → Redis SETEX account_locked:{userId} 900 1
            → إرجاع 429 "账号已被锁定，请15分钟后再试"
            → مسح العداد DEL account_lockout:{userId}
```

**السلوك خلال فترة القفل**:

خلال فترة القفل تُرجع جميع طلبات تسجيل الدخول 429 مباشرة دون التحقق من كلمة المرور، ما يمنع محاولات التخمين العنيف تمامًا.

**ثوابت التكوين**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_LOGIN_ATTEMPTS | 5 | الحد الأقصى لحالات الفشل المتتالية |
| LOCKOUT_DURATION | 900 | مدة القفل (بالثواني)، أي 15 دقيقة |

ملاحظة: قفل الحساب يعتمد على `userId` لا على الـ IP، لذا لا يمكن للمهاجم تجاوز القفل بتغيير الـ IP. وتتراكب مع حد الـ IP (10 مرات/دقيقة) لتشكيل حماية مزدوجة:
- على مستوى الـ IP: حد 10 مرات/دقيقة يمنع التخمين العنيف الموزع
- على مستوى الحساب: قفل بعد 5 حالات فشل يمنع التخمين العنيف الموجه

## 6. المصادقة والتفويض

### 6.1 مصادقة JWT

منفَّذة في وسيطة AdminAuth، ومثبتة على مجموعات المسارات التي تتطلب المصادقة.

**تكوين المعاملات** (`config/plugin/erikwang2013/jwt/jwt`، محقون عبر `.env`):

| المعامل | القيمة | الوصف |
|------|-----|------|
| الخوارزمية | HS256 | توقيع متماثل HMAC-SHA256 |
| المفتاح | `JWT_SECRET_KEY` | محقون عبر متغير البيئة، عند غيابه أو بقائه على القيمة الافتراضية يُرفض الإقلاع (fail-closed) |
| TTL لـ access_token | 7200s (2h) | `JWT_TTL` |
| TTL لـ refresh_token | 1209600s (14d) | `JWT_REFRESH_TTL` |
| المُصدِر | `open-admin` | `JWT_ISSUER` |
| الجمهور | `open-admin` | `JWT_AUDIENCE` |

**استخراج الرمز**: يُستخرج من ترويسة `Authorization: Bearer <token>`، وتُقص بادئة `Bearer ` للحصول على JWT الأصلي.

**تدفق المصادقة**:
1. رمز فارغ → 401 مباشرة `{"code": 401, "message": "未登录"}`
2. فحص القائمة السوداء في Redis `jwt_blacklist:{md5(token)}` → إصابة → 401 `Token已失效，请重新登录`
3. فك تشفير JWT → فشل (منتهي/توقيع غير مطابق) → 401 `Token已过期或无效`
4. نجاح → حقن `$request->adminId` و`$request->adminUsername`

**آلية القائمة السوداء**: عند تسجيل خروج المستخدم، يُكتب `md5(token)` في Redis مع TTL يساوي مدة JWT المتبقية. عند تعطل Redis يُتجاوز فحص القائمة السوداء (fail-open)، وعندها يمكن استخدام الرمز المسجل خروجه مؤقتًا، لكن المدة القصيرة لـ JWT نفسه (2h) تشكل حماية احتياطية.

**تحديث الرمز**: يتحقق `POST /api/auth/refresh` من رمز التحديث الأصلي (`token_type=refresh` وغير منتهٍ/غير مُدرج في القائمة السوداء) قبل إصدار رموز متجددة، ويتحقق من أن `sub` معرف مستخدم صالح — **لا يُصدر بعد الآن refresh token بقيمة sub=null**، وفشل التحديث يُرجع 401 مباشرة.

### 6.2 تقييد الجلسات المتزامنة

لمنع إساءة استخدام الرمز المسرب على أجهزة متعددة، يحد النظام عدد الرموز الصالحة التي يحملها نفس المستخدم في آنٍ واحد.

**منطق التقييد**:

```
نجاح تسجيل الدخول → إصدار رمز جديد
         → الاستعلام عن عدد الرموز الصالحة الحالية للمستخدم: Redis SCARD user_tokens:{userId}
         → إذا كان العدد >= 3 (MAX_CONCURRENT_SESSIONS):
            → الترتيب تصاعديًا حسب وقت الإنشاء، وإزالة أقدم رمز:
              Redis SREM user_tokens:{userId} <oldest_token_id>
              Redis SETEX jwt_blacklist:{md5(oldest_token)} TTL remaining
         → إضافة الرمز الجديد إلى المجموعة: Redis SADD user_tokens:{userId} <new_token_id>
            Redis SET user_token:{token_id} {userId} EX {TTL}
```

**ثوابت التكوين**:

| الثابت | القيمة | المعنى |
|------|-----|------|
| MAX_CONCURRENT_SESSIONS | 3 | الحد الأقصى للرموز المتزامنة لنفس المستخدم |

**سيناريو الخروج القسري**: عند تسجيل دخول المستخدم من الجهاز الرابع، يُضاف رمز الجهاز الأول قسريًا إلى القائمة السوداء، وتُرجع الطلبات اللاحقة 401 "Token已失效，请重新登录".

عند تسجيل الخروج، يُزال الرمز الحالي من المجموعة. وعند انتهاء صلاحية الرمز طبيعيًا، تنتهي صلاحية مفتاح Redis تلقائيًا وينخفض عدد أعضاء المجموعة.

### 6.3 نموذج صلاحيات RBAC

منفَّذة في وسيطة AdminPermission.

**نموذج البيانات**: ارتباط ثلاثي الطبقات User -> Role -> Permission

- `game_admin_user` (جدول المستخدمين)
- `game_admin_user_role` (جدول ربط المستخدم-الدور)
- `game_admin_role` (جدول الأدوار)
- `game_admin_role_permission` (جدول ربط الدور-الصلاحية)
- `game_admin_permission` (جدول الصلاحيات)

**أنواع الصلاحيات**:
| type | المعنى | مثال |
|------|------|------|
| 1 | صلاحية قائمة | التحكم في ظهور التنقل الأيسر |
| 2 | صلاحية زر | التحكم في أزرار العمليات داخل الصفحة (إضافة/تعديل/حذف) |
| 3 | صلاحية API | التحكم في استدعاء واجهات الخلفية |

تنسيق معرّف صلاحية API: `{method}.{path}`

مثال:
- `post.admin/user` — إنشاء مستخدم
- `put.admin/user` — تعديل مستخدم
- `delete.admin/user` — حذف مستخدم
- `get.admin/user` — عرض قائمة المستخدمين

**تدفق التفويض**:
1. `$request->adminId` فارغ (غير مسجل دخول) → 401 مباشرة `{"code": 401, "message": "未登录"}`، دون مزيد من التمرير
2. الحصول على المستخدم ← الأدوار (تخطي الأدوار المعطلة `status=0`) ← قائمة الصلاحيات
3. المدير الفائق (`slug = '*'`) → تمرير مباشر
4. بناء `strtolower(method) . '.' . trim(path, '/')` → المقارنة مع قائمة الصلاحيات
5. فشل المطابقة → 403 `{"code": 403, "message": "无权限访问"}`

**التأكيد الثانوي**: يوفر BaseController طريقة `confirmPassword()`، تتطلب العمليات الحساسة (حذف المستخدمين، تصدير البيانات وغيرها) على طبقة Controller إدخال كلمة المرور الحالية، لمنع عمليات غير مصرح بها بعد اختطاف الجلسة.

### 6.4 التحقق من توقيع رد الدفع (fail-closed)

يعتمد `POST /api/payment/callback` (رد تعبئة Stripe/PayPal) تحقق التوقيع بنمط **fail-closed**، أي غياب أي تكوين أو أي خلل في التحقق يرفض الرد:

| السيناريو | السلوك |
|------|------|
| Stripe بدون تكوين `STRIPE_WEBHOOK_SECRET` | رفض (403)، لا تُقبل ردود بلا توقيع بعد الآن |
| توقيع Stripe مفقود / فشل التحقق | رفض (403) |
| طابع Stripe الزمني `t=` مفقود أو فرق الوقت مع الخادم **> ±5 دقائق** | رفض (403)، منع إعادة التشغيل |
| PayPal بدون تكوين `PAYPAL_WEBHOOK_ID` | رفض (403) |
| خلل في التحقق الراجع من PayPal / غير SUCCESS | رفض (403) |
| بعد تكوين `CALLBACK_TRUSTED_IPS` الاختياري، عنوان IP المصدر ليس في القائمة البيضاء | رفض (403) |
| provider الرد لا يطابق طريقة دفع الطلب / طريقة الدفع غير موجودة | رفض (403) |

يتم إيداع الرد (تحديث الحالة + الرصيد + السجل) في نفس معاملة قاعدة البيانات، وأي خطوة تفشل يتراجع الكل، لمنع الإيداع النصف مكتمل.

## 7. سجلات التدقيق

### 7.1 سجلات العمليات

تسجل وسيطة OperationLog تلقائيًا سجلات العمليات لطلبات POST / PUT / DELETE. طلبات GET لا تُسجل.

**الحقول المسجلة**:

| الحقل | المصدر | الوصف |
|------|------|------|
| id | SnowflakeService::generate() | معرف فريد عالميًا |
| user_id | `$request->adminId` | معرف المنفذ، 0 عند عدم تسجيل الدخول |
| action | `$request->method()` | يساوي method |
| method | `$request->method()` | POST / PUT / DELETE |
| path | `$request->path()` | مسار الطلب |

**تصفية الحقول الحساسة**: تُستبدل قيم الحقول التالية بـ `***` باجتياز تكراري لجسم الطلب:

`password`, `old_password`, `new_password`, `new_password_confirmation`, `token`, `secret`, `access_token`, `refresh_token`

**كشف طرف المصدر** (`detectSource()`): حسب الأولوية:

1. قراءة الترويسة المخصصة `X-Client-Platform` أولاً (يعلنها العميل الأصلي صراحة)
2. التدهور إلى الاستدلال من سلسلة User-Agent (ترتيب كشف طريقة `detectSource()`):

| المنصة | كلمات UA الأساسية |
|------|----------|
| iPadOS | `iPad` |
| macOS | `Macintosh`, `Mac OS` |
| Windows | `Windows` |
| Linux | `Linux` |
| iOS | `iPhone`, `iOS`, `CFNetwork` |
| Android | `Android` |
| HarmonyOS | `HarmonyOS`, `OpenHarmony` |
| Web | القيمة الافتراضية الاحتياطية |

**تحمّل الأخطاء**: خلل كتابة السجل لا يعيق طلبات الأعمال (`catch (\Throwable)` يبتلع بصمت).

### 7.2 سجل الأمان

**موقع الملف**: `runtime/logs/security.log`

**المحتوى المسجل**:
- سجلات اعتراض الهجمات: فئة الهجوم، الـ IP، المسار، الحقل، المصدر، مقتطف payload (أول 200 حرف)
- إشعارات حظر الـ IP: الـ IP المحظور، عدد الإصابات

صلاحيات السجل `FILE_APPEND | LOCK_EX`، لضمان كتابة آمنة متزامنة.

## 8. حماية البيانات

يعتمد النظام استراتيجية حماية بيانات من ثلاث طبقات، تقابل المراحل الثلاث لتدفق البيانات.

### 8.1 طبقة النقل — EncryptionService

يستخدم `EncryptionService` حزمة `erikwang2013/encryption` لتشفير/فك تشفير الحقول الحساسة في طلبات/استجابات API.

**التفاصيل التقنية**:
- الخوارزمية: `aes-256-cbc-hmac` (بتوقيع HMAC مدمج يمنع العبث)
- المفتاح: متغير البيئة `ENCRYPTION_KEY`، يُحاذى تلقائيًا إلى 32 بايت
- الاستخدام: نقل حقول مثل أرقام الهواتف وأرقام الهوية بين العميل وAPI

**طرق أدوات الإخفاء**:
- `maskPhone('13812341234')` → `138****1234`
- `maskEmail('abc@example.com')` → `a***@example.com` (اسم المستخدم أكثر من حرفين) أو `a**@example.com`

### 8.2 طبقة التخزين — Encryptable Cast

يستخدم نموذج `AdminUser` cast Eloquent من `Erikwang2013\Encryptable\Encryptable`، والحقول المقابلة:

- `email` → cast إلى Encryptable، تشفير/فك تشفير تلقائي
- `phone` → cast إلى Encryptable، تشفير/فك تشفير تلقائي
- `id_card` → cast إلى Encryptable، تشفير/فك تشفير تلقائي

عند الكتابة إلى قاعدة البيانات تُشفَّر تلقائيًا إلى نص مشفر، وعند القراءة تُفك تلقائيًا إلى نص واضح. نوع عمود التخزين في قاعدة البيانات `VARCHAR(500)`، ويُخزَّن النص المشفر بصيغة base64.

**نظام المفاتيح**: يستخدم `ENCRYPTABLE_KEY` مستقلًا عن تشفير طبقة النقل (`ENCRYPTION_KEY`)، فلا يكشف تسريب مفتاح واحد الطبقة الأخرى.

تدوير المفاتيح: يدعم متغير البيئة `ENCRYPTION_PREVIOUS_KEYS` قائمة المفاتيح التاريخية (مفصولة بفواصل)، فعند قراءة البيانات القديمة تُجرَّب المفاتيح التاريخية لفك التشفير، وعند الكتابة يُستخدم المفتاح الحالي لإعادة التشفير.

### 8.3 طبقة العرض — إخفاء المعرفات وتنكرها

**إخفاء معرفات Hashids**: يستخدم `HashidsService` حزمة `erikwang2013/hashids`.

- تُرمَّز معرفات قاعدة البيانات BIGINT التي تُرجعها واجهات API الخارجية إلى سلاسل hash (مثل `xK3mN9qR2pL7wV8b`)
- يمرر العميل سلسلة hash عند الطلب، وتفكها الخلفية تلقائيًا إلى المعرف الأصلي
- الملح `HASHIDS_SALT` محقون عبر متغير البيئة، واختلاف الملح يعني نتائج ترميز/فك ترميز مختلفة تمامًا
- الحد الأدنى لطول hash 16 خانة، باستخدام مجموعة أحرف أبجدية رقمية من 62 خانة
- يوفر BaseController طرقًا ميسرة `encodeId()` و`decodeId()` و`encodeIds()`

**إخفاء التصدير**: عند تصدير Excel/PDF (في ExportController)، تُخفى الحقول الحساسة بشكل موحد:
- رقم الهاتف: `138****1234`
- البريد الإلكتروني: `a***@example.com`
- رقم الهوية: تغطية كاملة بـ `********`

## 10. security.txt (RFC 9116)

يوفر النظام في `/.well-known/security.txt` نقطة نهاية بمعلومات الاتصال الأمنية المتوافقة مع RFC 9116، لتسهيل وصول باحثي الأمان إلى قناة الإبلاغ عند اكتشاف ثغرات.

**طريقة الوصول**:

```
GET /.well-known/security.txt
```

**محتوى الاستجابة**:

```text
Contact: mailto:security@erik.xyz
Expires: 2027-05-20T00:00:00.000Z
Preferred-Languages: zh, en
Canonical: https://erik.xyz/.well-known/security.txt
Policy: https://erik.xyz/security-policy
```

**شرح الحقول**:

| الحقل | الوصف |
|------|------|
| Contact | وسيلة الاتصال للإبلاغ عن الثغرات الأمنية |
| Expires | وقت انتهاء صلاحية الملف، يتطلب تحديثًا دوريًا |
| Preferred-Languages | اللغة المفضلة للتواصل |
| Canonical | URL الرسمي لهذا الملف |
| Policy | رابط سياسة الأمان/سياسة الإفصاح عن الثغرات |

لا تخضع هذه النقطة للحد من المعدل أو المصادقة أو غيرها من الوسيطات، ويمكن لأي شخص الوصول إليها مباشرة.

## 11. تكوين أمان Nginx

يوفر المشروع `docs/nginx-security.conf` كتكوين مرجعي لتحصين الوكيل العكسي في بيئة الإنتاج.

**الإجراءات الأمنية المتضمنة**:

| عنصر التكوين | الوظيفة |
|--------|------|
| `server_tokens off` | إخفاء رقم إصدار Nginx |
| `client_max_body_size 10m` | تقييد حجم جسم الطلب، بالتنسيق مع SecurityFilter |
| `limit_req_zone` | تقييد تواتر الطلبات على مستوى Nginx |
| `limit_conn_zone` | تقييد عدد الاتصالات المتزامنة |
| ترويسات `add_header` الأمنية | إضافة ترويسات أمنية مثل X-XSS-Protection على مستوى Nginx |
| `if ($request_method)` | رفض طرق HTTP غير القياسية على مستوى Nginx |
| تكوين SSL/TLS | تكوين حديث TLS 1.2/1.3، وتعطيل مجموعات التشفير الضعيفة |
| إخفاء ترويسات الخلفية | `proxy_hide_header` لإزالة الترويسات الحساسة مثل إصدار webman |

**طريقة الاستخدام**: ادمج تكوين `docs/nginx-security.conf` في كتلة server في Nginx لديك، وعدّله حسب نطاقك الفعلي ومسار الشهادات.
