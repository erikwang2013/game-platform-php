## Быстрый старт

### 1. Установка зависимостей

```bash
composer install
```

### 2. Настройка переменных окружения

Скопируйте и измените переменные окружения (опционально, если не заданы — используются значения по умолчанию из `config/*.php`):

```bash
cp .env.example .env
```

Ключевые настройки:

| Переменная окружения | Описание | Значение по умолчанию |
|---------|------|--------|
| `JWT_SECRET` | Секрет подписи JWT | `open-admin-jwt-secret-change-in-production` |
| `HASHIDS_SALT` | Соль Hashids | `open-admin-hashids-salt-2026` |
| `ENCRYPTION_KEY` | Ключ шифрования API | 32-байтовое значение по умолчанию |
| `SNOWFLAKE_DATACENTER_ID` | ID центра обработки данных (0-31) | `1` |
| `SNOWFLAKE_WORKER_ID` | ID рабочего узла (0-31) | `1` |
| `SCOUT_HOSTS` | Адрес ES | `http://localhost:9200` |

**В продакшене обязательно замените все ключи на случайные строки.**

### 3. Инициализация базы данных

Выполните по порядку SQL-файлы из `install/`:

```bash
mysql -u root -p < install/install.sql
```

### 4. Запуск сервиса

```bash
php start.php start
```

По умолчанию слушает `http://0.0.0.0:8787`.

### 5. Запуск фронтенда (опционально)

**Flutter админ-панель (Web):**

```bash
cd apps/flutter
flutter pub get
flutter run -d chrome    # Web-версия (стиль PC-панели)
```

**Клиент HarmonyOS (мобильный):**

Откройте каталог `apps/harmonyos/` в DevEco Studio и запустите на реальном устройстве или эмуляторе.

### 6. Развертывание Docker Compose в один клик (рекомендуется для продакшена)

Проект включает полную Docker-оркестрацию из 5 сервисов: Nginx, PHP (webman app), MySQL, Redis, Elasticsearch.

```bash
# 1. Настройте переменные окружения Docker
cp .env.docker .env

# 2. Запустите все сервисы
docker-compose up -d

# 3. Инициализируйте базу данных (выполните внутри контейнера app)
docker-compose exec app mysql -h mysql -u root -p < install/install.sql

# 4. Доступ
# http://localhost:8787  (webman)
# http://localhost:8080  (обратный прокси Nginx)
```

- `Dockerfile`: PHP 8.3 + OPcache + Composer, на базе `php:8.3-cli`
- `docker-compose.yml`: оркестрация 5 сервисов, изоляция сети, персистентность томов данных
- `.env.docker`: переменные окружения для Docker


## Стандарты базы данных

- **Префикс таблиц**: `game_`
- **Первичный ключ**: у всех таблиц `id BIGINT UNSIGNED NOT NULL`, **AUTO_INCREMENT запрещен**
- **Генерация ID**: первичные ключи генерируются на уровне приложения `SnowflakeService::generate()`, распределенно уникальны
- **Обязательные поля**: каждая таблица должна содержать `id`, `created_at`, `updated_at`
- **Мягкое удаление**: для таблиц с мягким удалением добавляется `deleted_at DATETIME DEFAULT NULL`
- **Чувствительные поля**: телефон, email, удостоверение личности и т.п. шифруются/дешифруются автоматически плагином `encryptable`, в БД хранится шифротекст в `VARCHAR(500)`

## Стандарты API

### Единый формат ответа

```json
{
    "code": 0,
    "message": "success",
    "data": {}
}
```

### Бизнес-коды ошибок

| Код ошибки | Значение | Описание |
|-------|------|------|
| `0` | Успех | |
| `400` | Ошибка параметров запроса | |
| `401` | Не авторизован (токен недействителен или истек) | |
| `403` | Нет прав / блокировка безопасности | Неудача RBAC / обнаружение атаки SecurityFilter |
| `404` | Ресурс не найден | |
| `422` | Неудача проверки параметров | |
| `413` | Слишком большое тело запроса | Срабатывание SecurityFilter, более 10MB |
| `405` | Метод не разрешен | Срабатывание SecurityFilter, разрешены только GET/POST/PUT/DELETE/OPTIONS/HEAD |
| `415` | Неподдерживаемый тип медиа | Срабатывание SecurityFilter, Content-Type не JSON |
| `429` | Слишком частые запросы | Срабатывание RateLimit / блокировка аккаунта (5 неудачных входов — блокировка 15 минут) |
| `500` | Внутренняя ошибка сервера | |

### Обработка ID

- **ID в запросах/ответах**: шифруются в строки через hashids, реальные ID из БД не раскрываются
- **Пути интерфейсов**: `GET /admin/user/{hashid}` — `{id}` в пути это строка hashid
- **Хранение в БД**: исходное значение BIGINT, генерируется snowflake

### Версия API

Версия API задается заголовком запроса, **не отражается в URL**:

```http
API-Version: v1
```

- При отсутствии версии по умолчанию используется `v1`
- Неподдерживаемая версия возвращает `400 Bad Request`
- Для добавления версии достаточно создать каталог `app/api/{version}/controller/` и зарегистрировать новую версию в промежуточном ПО

### Ограничение частоты

На основе алгоритма скользящего окна Redis, по умолчанию 60 раз/мин/IP/маршрут. Для чувствительных интерфейсов строже:
- Вход: 10 раз/мин
- Регистрация: 5 раз/мин

Заголовки ответа содержат `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`. При превышении возвращается 429 с `Retry-After`.

### Архитектура промежуточного ПО

Глобальное промежуточное ПО действует на все запросы, выполняется по порядку:

```
Cors (предобработка CORS + заголовки ответа)
  → SecurityFilter (ограничение HTTP-методов/размер тела/проверка Content-Type/XSS/SQL-инъекции/обход пути/инъекции команд/CSRF)
  → RateLimit (скользящее окно Redis + блокировка аккаунта: 5 неудачных входов — блокировка 15 минут)
  → ApiVersion (проверка версии API, группа маршрутов /api)
  → AdminAuth (JWT-аутентификация + черный список, группа маршрутов /admin)
  → AdminPermission (RBAC-авторизация, группа маршрутов /admin)
  → OperationLog (автоматическая запись POST/PUT/DELETE, включая определение источника, группа маршрутов /admin)
```

`/health` и `/api/docs` — публичные эндпоинты, проходят только через `Cors → SecurityFilter → RateLimit`.

Усиление безопасности:
- **Блокировка аккаунта**: 5 неудачных входов подряд — автоматическая блокировка на 15 минут, вход в этот период возвращает 429
- **Ограничение параллельных сессий**: не более 3 действительных токенов на пользователя, при превышении самый старый токен автоматически попадает в черный список
- **security.txt**: `GET /.well-known/security.txt` предоставляет контактную информацию безопасности по стандарту RFC 9116
- **Конфигурация безопасности Nginx**: см. `docs/nginx-security.conf` — полный пример усиления безопасности обратного прокси

### Аутентификация

Вход и регистрация требуют предварительной проверки **клик-капчи**:

1. Клиент запрашивает `POST /api/captcha/generate` и получает изображение капчи (base64 PNG) и список текстовых целей
2. Пользователь кликает по соответствующим текстам на изображении по порядку, собираются координаты кликов `[{x, y}, ...]`
3. При входе вместе с данными отправляются `captcha_key` и `clicks`, сервер сначала проверяет капчу, затем учетные данные

```http
POST /api/auth/login
Content-Type: application/json

{
  "username": "admin",
  "password": "******",
  "captcha_key": "abc123...",
  "clicks": [{"x": 120, "y": 85}, {"x": 210, "y": 140}, {"x": 95, "y": 170}]
}
```

Дальнейшие интерфейсы панели требуют JWT-аутентификации:

```http
Authorization: Bearer <token>
```

После успешного входа возвращается access_token сроком действия 2 часа; также возвращается refresh_token сроком действия 14 дней.

При выходе токен добавляется в черный список Redis и не может использоваться до истечения срока. POST /admin/profile/logout

### Повторное подтверждение чувствительных операций

Для чувствительных операций (удаление пользователя, роли, прав и т.п.) в теле запроса необходимо передать `password` текущего вошедшего пользователя для повторного подтверждения личности:

```http
DELETE /admin/user/{id}
Content-Type: application/json
Authorization: Bearer <token>

{ "password": "******" }
```

| `POST` | `/admin/upload` | Загрузка файлов (изображения/документы, максимум 10MB) |

## Примечания по фронтенду

### Flutter админ-панель (PC-стиль)

- **Раскладка**: сайдбар (сворачиваемый 64px/240px) + шапка + контент, адаптивные три брейкпоинта (телефон/планшет/десктоп)
- **Страницы**: вход, дашборд, управление пользователями, роли и права, системные настройки, журнал операций, личный кабинет
- **Управление состоянием**: GetX (синглтон `ApiService` + персистентность токена `AuthService`)
- **Дашборд**: карточки статистики, линейный график трендов (fl_chart), круговая диаграмма, последние операции
- **Экспорт**: экспорт Excel/PDF, в PDF — неудаляемая информация об авторских правах
- **Массовые операции**: массовое удаление по выбору, массовое включение/отключение
- **Тема**: Material 3, светлая/темная темы

### Мобильная версия HarmonyOS

- **Страницы**: вход, дашборд, список/детали пользователей, личный кабинет
- **Аутентификация**: JWT Bearer + бесшовное обновление токена при 401, при неудаче — автоматический переход на страницу входа
- **Хранение**: токен через AppStorage

## Стандарты разработки

- Глобальные функции/классы не имеют префикса `\`, используется импорт через `use`
- Все PHP-файлы должны содержать объявление авторских прав в шапке
- Все файлы конфигурации должны содержать комментарии на китайском
- Первичные ключи БД должны генерироваться snowflake на уровне приложения, автоинкремент запрещен
- Все ID в параметрах и ответах API должны шифроваться/дешифроваться через hashids
- Промежуточное ПО AdminPermission кэширует права пользователя в Redis (TTL=60s), устраняя узкое место N+1

## Развертывание

### Docker Compose (рекомендуется)

В корне проекта есть `docker-compose.yml` с оркестрацией 5 сервисов:

| Сервис | Образ | Порт |
|------|------|------|
| `nginx` | nginx:alpine | 80, 443 |
| `app` | сборка из локального `Dockerfile` | 8787 |
| `mysql` | mysql:8.0 | 3306 |
| `redis` | redis:7-alpine | 6379 |
| `elasticsearch` | elasticsearch:8.x | 9200 |

PHP-образ собирается через `Dockerfile`, базовый образ `php:8.3-cli`, включен OPcache.

```bash
cp .env.docker .env
docker-compose up -d
```

### CI/CD

Конвейер непрерывной интеграции GitHub Actions: `.github/workflows/ci.yml`

- Проверка синтаксиса PHP (`php -l`)
- Модульные тесты PHPUnit
- Статический анализ Flutter (`flutter analyze`)

### Резервное копирование базы данных

Каталог `database/backup/`:

- `backup.sh` — резервное копирование mysqldump + gzip, автоочистка старых копий старше 30 дней
- `restore.sh` — интерактивное восстановление, вывод списка доступных копий для выбора

Для продакшена см. `docs/nginx-security.conf` — усиление безопасности обратного прокси.
