## 1. تصميم نظام العملات

### 1.1 نموذج العملات ثلاثي الطبقات

```
الطبقة 1: العملات القانونية (USD / CNY / EUR / JPY ...)
       ↕ شحن/سحب (بالتحويل وفق سعر الصرف)
الطبقة 2: عملات المنصة (موحدة، الدقة decimal(18,4))
       ↕ استبدال (يشمل سعر الصرف + فرق عمولة المنصة)
الطبقة 3: عملات الألعاب (مستقلة لكل لعبة، سعر صرف مستقل)
```

### 1.2 عملات المنصة

- وحدة التسعير الموحدة داخل المنصة
- الدقة: `DECIMAL(18,4)`، أصغر وحدة 0.0001
- تُكتسب بالشحن بالعملات القانونية، ويمكن استبدالها بأي عملة لعبة
- يمكن أيضًا استبدال عملات الألعاب إلى عملات المنصة، ثم سحبها إلى عملة قانونية
- تفرض المنصة فرق الاستبدال كمصدر دخل

### 1.3 عملات الألعاب

- لكل لعبة يمكن أن يكون لها عدة عملات (مثل الذهب والماس والنقاط)
- لكل عملة سعر صرف مستقل مقابل عملة المنصة (`exchange_rate`)
- لكل عملة نسبة عمولة منصة مستقلة (`spread_pct`)
- دعم تعيين الحد الأدنى/الأقصى للاستبدال (`min_exchange` / `max_exchange`)

### 1.4 صيغة الاستبدال

**شراء عملات اللعبة (عملة المنصة → عملة اللعبة):**
```
عملات اللعبة المستلمة = كمية عملة المنصة × exchange_rate × (1 - spread_pct / 100)
```

**بيع عملات اللعبة (عملة اللعبة → عملة المنصة):**
```
عملات المنصة المستلمة = كمية عملة اللعبة ÷ exchange_rate × (1 - spread_pct / 100)
```

**مثال:**
- exchange_rate = 100 (1 عملة منصة = 100 عملة لعبة)
- spread_pct = 5% (عمولة المنصة 5% فرقًا)
- يشتري المستخدم بـ 10 عملات منصة: (10 × 100 × 0.95) = 950 عملة لعبة
- يبيع المستخدم 950 عملة لعبة: (950 ÷ 100 × 0.95) = 9.025 عملة منصة
- إيراد المنصة: 10 - 9.025 = 0.975 عملة منصة

## 2. تصميم المحفظة

### 2.1 محفظة عملات المنصة (erik_user_wallet)

تُنشأ تلقائيًا عند تسجيل المستخدم، الرصيد الابتدائي 0.

| الحقل | الوصف |
|------|------|
| balance | الرصيد المتاح (قابل للشحن/السحب/الاستبدال) |
| frozen_balance | الرصيد المجمد (محتجز، مثل أثناء السحب) |
| total_earned | الإيراد التراكمي |
| total_spent | الإنفاق التراكمي |
| version | رقم إصدار القفل التفاؤلي (يزيد +1 عند كل تحديث) |

### 2.2 محفظة عملات الألعاب (erik_user_game_wallet)

فريدة ثلاثيًا حسب المستخدم + اللعبة + العملة. تُنشأ تلقائيًا عند أول استبدال.

### 2.3 أمان التزامن

يُستخدم القفل التفاؤلي لمنع مشاكل التزامن:

```php
// فحص رقم الإصدار عند التحديث
$updated = Wallet::where('id', $wallet->id)
    ->where('version', $wallet->version)
    ->update([
        'balance' => bcadd($wallet->balance, $amount, 4),
        'version' => $wallet->version + 1,
    ]);

// فشل التحديث (تغيّر رقم الإصدار) → إعادة المحاولة، حتى 5 مرات
```

## 3. تصميم نظام السحب

### 3.1 تحكم متعدد الطبقات

```
الطبقة 1: المفتاح العام للسحب
       ├─ مغلق → رفض جميع السحوبات، للتحكم في المخاطر الطارئة
       └─ مفتوح → الدخول في فحص الطبقة 2

الطبقة 2: فحص الحدود
       ├─ الحد الأدنى للعملية الواحدة (min_amount)
       ├─ الحد الأقصى للعملية الواحدة (max_amount)
       └─ الحد التراكمي اليومي (daily_limit)

الطبقة 3: عملية المراجعة
       ├─ المبلغ < عتبة المراجعة التلقائية → موافقة تلقائية
       └─ المبلغ >= عتبة المراجعة التلقائية → مراجعة بشرية → موافقة/رفض
```

### 3.2 آلة حالات السحب

```
pending (قيد المراجعة)
  ├─→ approved (تمت الموافقة) → completed (مكتمل)
  └─→ rejected (مرفوض) → إعادة الرصيد + سجل الاسترداد
```

### 3.3 تحكم لوحة الإدارة

- **زر المفتاح العام**: فتح/إغلاق سحوبات جميع المستخدمين بنقرة واحدة
- **قائمة المراجعة**: قائمة قيد المراجعة مرتبة زمنيًا، مع أزرار موافقة/رفض
- **إعداد الحدود**: ضبط معاملات الحدود بشكل مرئي

## 4. تصميم الشحن

### 4.1 عملية الشحن

```
1. يختار المستخدم طريقة الدفع والمبلغ
2. تنشئ المنصة طلب شحن (status=pending، توليد order_no فريد)
3. الانتقال إلى صفحة الدفع عبر الطرف الثالث
4. يكمل المستخدم الدفع
5. يستدعي الطرف الثالث إشعار المنصة (POST /api/payment/callback)
6. تتحقق المنصة من التوقيع → تحديث الطلب (status=confirmed)
7. إيداع عملات المنصة → تسجيل الحركة
```

### 4.2 طرق الدفع

| النوع | المزود | الوصف |
|------|--------|------|
| عملة قانونية | Stripe | الدفع بالبطاقات الائتمانية الدولية |
| عملة قانونية | PayPal | المحفظة الإلكترونية العالمية |
| عملة قانونية | Alipay | علي باي (البر الرئيسي للصين) |
| عملة قانونية | WeChat Pay | وي تشات باي (البر الرئيسي للصين) |
| عملة مشفرة | USDT-TRC20 | USDT على سلسلة ترون |

يربط الإصدار الأساسي أولًا طريقة دفع واحدة (مثل Stripe)، ويوسّع الإصدار القياسي جميع القنوات.

## 5. تصميم تكامل الألعاب

### 5.1 الألعاب المطوّرة ذاتيًا

تتكامل الألعاب المطوّرة ذاتيًا مباشرة في المنصة، وتشارك نظام المستخدمين والمحفظة:

- تستعلم اللعبة عن رصيد عملات اللعبة للمستخدم عبر واجهة داخلية
- تسوية اللعبة عبر واجهة داخلية لخصم/زيادة عملات اللعبة
- لا حاجة للتحقق الإضافي من التوقيع

### 5.2 الألعاب من طرف ثالث

تُربط ألعاب الطرف الثالث عبر SDK/API:

```
جانب المنصة:
  1. ينقر المستخدم على "دخول اللعبة"
  2. تولّد المنصة توقيعًا (user_id + timestamp + api_secret → HMAC-SHA256)
  3. إعادة توجيه 302 أو تحميل iframe لعنوان اللعبة (مع معاملات التوقيع)

جانب اللعبة:
  4. التحقق من التوقيع → إنشاء جلسة اللعبة
  5. الاستعلام عن الرصيد: GET /api/game/balance?user_id=...&sign=...
  6. استدعاء التسوية: POST /api/game/callback {user_id, amount, type, sign}
  7. تتحقق المنصة من التوقيع → تحديث الرصيد → تسجيل الحركة → إرجاع النتيجة
```

### 5.3 خوارزمية التوقيع

```
signature = HMAC-SHA256(
    secret = api_secret,
    message = user_id + "|" + timestamp + "|" + amount + "|" + nonce,
)
```

شروط التحقق:
- التوقيع صحيح
- الطابع الزمني ضمن ±60 ثانية (الحماية من replay attack)
- nonce غير مستخدم مسبقًا (مسجّل في Redis، ينتهي خلال 60 ثانية)
- عنوان IP للطلب ضمن القائمة البيضاء

## 6. تصميم الصلاحيات

### 6.1 الأدوار الجاهزة

| الدور | نطاق الصلاحية |
|------|---------|
| المشرف الفائق | * (جميع الصلاحيات) |
| تشغيل الألعاب | إدارة الألعاب، إدارة الإعلانات، لوحة التحكم |
| مراجعة المالية | مراجعة السحب، إدارة الدفع، عرض الحركات |
| خدمة العملاء | عرض مستخدمي الطرف C، عرض طلبات الشحن |

### 6.2 درجة الصلاحية

```
{method}.{path}

أمثلة:
  get.admin/game/list      → عرض قائمة الألعاب
  post.admin/game/create   → إنشاء لعبة
  put.admin/withdraw/review → مراجعة السحب
  put.admin/withdraw/switch → التعامل مع مفتاح السحب (المشرف الفائق فقط)
```

## 呼. تصاميم الإصدار القياسي الجديدة

### 8.1 محرك إدارة المخاطر

أربعة أنواع من القواعد:
- `ip_blacklist` — مطابقة قائمة IP السوداء، حظر فوري عند الإصابة
- `amount_anomaly` — كشف المبالغ الكبيرة للعملية الواحدة، إنذار عند تجاوز العتبة
- `frequency` — كشف تكرار العمليات داخل نافذة زمنية
- `velocity` — كشف ارتباط الحسابات المتعددة في فترة قصيرة

تُنفَّذ القواعد تنازليًا حسب priority، وأول قاعدة مطابقة تحدد النتيجة (block > warn > log).

### 8.2 تسجيل دخول OAuth بطرف ثالث

المزودون المدعومون: Google وFacebook وApple

العملية:
1. تطلب الواجهة الأمامية `GET /api/auth/oauth/{provider}` للحصول على عنوان التفويض
2. ينتقل المستخدم إلى الطرف الثالث لإكمال التفويض
3. الاستدعاء `POST /api/auth/oauth/{provider}/callback` يحمل رمز التفويض
4. يبحث الخلفي عن ربط موجود → تسجيل دخول مباشر؛ لا ربط → تسجيل تلقائي + ربط + إنشاء محفظة

### 8.3 نظام حدود KYC

| المستوى | طريقة الحصول | الحد الأقصى للعملية الواحدة | الحد اليومي | الرسوم |
|------|---------|---------|--------|--------|
| default | افتراضي عند التسجيل | 1,000 | 10,000 | 1.00% |
| verified | اجتياز مراجعة KYC | 5,000 | 50,000 | 0.50% |
| vip | منح من التشغيل | 20,000 | 200,000 | 0.00% |

### 8.4 خوادم الألعاب

لكل لعبة يمكن إعداد عدة خوادم (region: global/asia/eu/na)، حالات الخادم: صيانة/عادي/مزدحم/خادم جديد.

### 8.5 لقطة الإحصائيات اليومية

ينفّذ crontab يوميًا في الفجر `ComputeDailyStats::run()`، ويحسب خمسة مؤشرات:
- إحصائيات المستخدمين (جدد/نشطون/تراكمي)
- إحصائيات الشحن (عدد الطلبات/المبلغ الإجمالي)
- إحصائيات السحب (عدد الطلبات/المبلغ الإجمالي)
- إحصائيات الاستبدال (عدد الطلبات/إجمالي الرسوم)
- إحصائيات الألعاب (عدد اللاعبين/عدد الجلسات)

## 9. وظائف بمستوى الإنتاج

### 9.1 نظام الإشعارات

أنواع الإشعارات: system/deposit/withdraw/kyc/coupon/announcement

السيناريوهات التلقائية:
- وصول الشحن → NotificationService::send()
- موافقة/رفض مراجعة السحب → إشعار تلقائي
- موافقة/رفض مراجعة KYC → إشعار تلقائي
- استلام قسيمة → إشعار تلقائي
- وصول مكافأة الإحالة → إشعار تلقائي

يدعم القناتين: رسائل داخل الموقع + البريد الإلكتروني (البريد يتطلب إعداد متغير البيئة MAIL_HOST).

### 9.2 عمولة الإحالة

```
المستخدم A يولّد رمز إحالة → يشاركه مع المستخدم B
يسجل المستخدم B معبئًا رمز الإحالة → يحصل الطرفان على مكافأة التسجيل (signup_reward)
يشحن المستخدم B → يحصل A على عمولة الشحن (deposit_commission_pct%)
```

### 9.3 المصادقة الثنائية 2FA

- بروتوكول TOTP القياسي (RFC 6238)، متوافق مع Google Authenticator
- عملية التفعيل: الحصول على المفتاح → مسح رمز QR للربط → التحقق من TOTP → توليد 8 رموز استرداد احتياطية
- التحقق الثاني عند تسجيل الدخول: POST /api/2fa/verify
- دعم تحمل نافذة زمنية ±1 (30 ثانية)

### 9.4 ربط OAuth حقيقي

| المزود | نقطة نهاية Token | نقطة نهاية معلومات المستخدم |
|--------|----------|------------|
| Google | oauth2.googleapis.com/token | www.googleapis.com/oauth2/v3/userinfo |
| Facebook | graph.facebook.com/v18.0/oauth/access_token | graph.facebook.com/me |
| Apple | appleid.apple.com/auth/token | فك ترميز JWT id_token |

الإعداد عبر PlatformConfig أو متغيرات البيئة، وعند فشل الطلب يعود تلقائيًا إلى وضع mock.

### 9.5 التحقق من توقيع Webhook الدفع

- Stripe: التحقق من توقيع HMAC-SHA256 (رأس Stripe-Signature)
- PayPal: POST إعادة الاستدعاء إلى نقطة تحقق PayPal
- تخطي التحقق تلقائيًا عند عدم إعداد المفتاح (وضع التطوير)

### 9.6 WebSocket لوحات المتصدرين اللحظية

- البروتوكول: WebSocket (ws://host:8789)
- الاشتراك: {action: "subscribe", leaderboard_id: 123}
- الدفع: {type: "ranking_update", rankings: [...]}
- دعم ping/pong لإبقاء الاتصال حيًا

## 7. تصميم التدويل

### 7.1 اللغات المدعومة

| الرمز | الاسم | اللغة المحلية | الأيقونة |
|------|------|--------|------|
| en-US | English | English | us |
| zh-CN | Chinese (Simplified) | 简体中文 | cn |
| ja-JP | Japanese | 日本語 | jp |
| ko-KR | Korean | 한국어 | kr |

### 7.2 إدارة الترجمات

- تُنظَّم الترجمات بصيغة `group.key` (مثل `auth.login_success`)
- تخزين في جدول `erik_translation`، تخزين مؤقت Redis (TTL ساعة واحدة)
- الواجهات: `GET /api/language/list` للحصول على اللغات المتاحة، `POST /api/language/switch` لتبديل اللغة
- كشف تلقائي في الواجهة الأمامية عبر رأس `X-Language` أو `Accept-Language`
- عند غياب الترجمة تراجع إلى en-US، وعند غيابها في en-US أيضًا يُرجع المفتاح الأصلي

### 7.3 تفضيل لغة المستخدم

- عند التسجيل تُضبط تلقائيًا حسب `Accept-Language` في المتصفح
- بعد تسجيل الدخول يمكن تعديل حقل `language` عبر `PUT /api/user/profile`
- عند تبديل اللغة تُحدَّث سجل المستخدم في نفس الوقت

## 8. نموذج إيراد المنصة

| مصدر الإيراد | طريقة الحساب | الوصف |
|---------|---------|------|
| فرق الاستبدال | spread_fee لكل عملية استبدال | تُحصَّل من الشراء والبيع معًا |
| رسوم السحب | مبلغ السحب × fee_pct | يُنفَّذ في الإصدار القياسي |
| تقاسم الألعاب | تقاسم إيراد ألعاب الطرف الثالث | حسب الاتفاق التعاقدي |
| فرق صرف الشحن | فرق سعر صرف العملة القانونية → عملة المنصة | الفرق بين سعر صرف المنصة وسعر السوق |
