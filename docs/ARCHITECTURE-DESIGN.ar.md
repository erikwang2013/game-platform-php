## 1. أهداف التصميم

بناء منصة تجميع ألعاب عالمية ودولية. المتطلبات الأساسية:

- يمكن للمستخدمين الشحن على المنصة، واستبدال عملات الألعاب، ولعب الألعاب، وكسب عملات الألعاب، والسحب
- تدير المنصة موحدًا أنواعًا متعددة من الألعاب (مطوّرة ذاتيًا + طرف ثالث)، ولكل لعبة عملة مستقلة وسعر صرف
- يوفر الخلفي قدرات كاملة للمراجعة والمفاتيح وإدارة المخاطر
- دعم التشغيل العالمي متعدد اللغات ومتعدد العملات ومتعدد قنوات الدفع

## 2. اختيار البنية

### 2.1 لماذا اخترنا الوحدة المتجانسة المعيارية بدلًا من الخدمات المصغرة؟

في المرحلة الحالية نختار الوحدة المتجانسة المعيارية (Modular Monolith):

| الاعتبار | الوحدة المتجانسة المعيارية | الخدمات المصغرة |
|------|----------|--------|
| كفاءة التطوير | استدعاء داخل نفس العملية، بدون RPC | يحتاج معالجة تأخير الشبكة والتسلسل |
| تناسق المعاملات | معاملات قاعدة بيانات محلية | معاملات موزعة (معقدة) |
| تعقيد التشغيل | نشر عملية واحدة | تنسيق خدمات متعددة واكتشاف الخدمات |
| قابلية التوسع | يمكن مستقبلًا تقسيمها إلى خدمات مصغرة حسب الوحدات | تدعم بطبيعتها التوسع والانكماش المستقلين |
| حجم الفريق | مناسب للفرق الصغيرة (1-5 أشخاص) | مناسب لتطوير متوازٍ لعدة فرق |

**القرار**: admin/ (لوحة الإدارة) وservice/ (أعمال الطرف C) هما مثيلان مستقلان من webman، يمكن نشرهما على نفس الجهاز (منافذ مختلفة) أو نشرهما منفصلين. الطبقة المشتركة common/ تلغي تكرار الكود عبر PSR-4 autoload. بعد نمو حجم الأعمال مستقبلًا، يمكن تقسيم service/ إلى عدة خدمات مصغرة (خدمة المستخدمين، خدمة المحافظ، خدمة الألعاب).

### 2.2 لماذا اخترنا webman v2 بدلًا من PHP-FPM التقليدي؟

| الاعتبار | webman v2 | PHP-FPM (Laravel) |
|------|-----------|-------------------|
| الأداء | ذاكرة مقيمة، دعم الكوروتين | تحميل جميع الملفات في كل طلب |
| التزامن | عشرات آلاف QPS على جهاز واحد | مئات QPS على جهاز واحد |
| النشر | بسيط، عملية واحدة متعددة العمال | إعداد Nginx + PHP-FPM معقد |
| النظام البيئي | متوافق مع مكونات Laravel Illuminate | نظام بيئي كامل |

**القرار**: يحتاج منصة الألعاب إلى معالجة استدعاءات الشحن عالية التزامن وطلبات الاستبدال وتسوية الألعاب؛ لذا فإن الذاكرة المقيمة وقدرة التزامن العالية في webman أنسب. وفي الوقت نفسه يتوافق مع ORM وQueue ومكونات Laravel الأخرى، فلا تقل كفاءة التطوير عن الأطر التقليدية.

### 2.3 لماذا نستخدم أسلوب Flutter Web PC؟

- كود واحد يمكن تجميعه في نفس الوقت إلى Web (PC) وiOS وAndroid وHarmonyOS
- مكتبة مكونات Material 3 ناضجة، وتخطيط PC بأسلوب الشريط الجانبي + الشريط العلوي جاهز للاستخدام
- مشاركة طبقة منطق الأعمال مع عميل HarmonyOS
- تجنب صيانة مجموعتي كود أماميتين React/Vue + Flutter

## 3. قرارات تقنية رئيسية

### 3.1 نظام المعرّفات

```
Snowflake يولد BIGINT (فريد موزع داخليًا)
    ↓
Hashids يشفرها إلى سلاسل قصيرة (لا يمكن استنتاج المعرّف الحقيقي خارجيًا)
    ↓
تُنقل سلسلة hashid في طلبات/استجابات API
```

**الأسباب**:
- Snowflake فريد عالميًا وذو اتجاه تزايدي مفيد للفهارس، ولا يكشف حجم الأعمال
- يمنع Hashids عبور البيانات خارجيًا عبر معرّفات ذاتية التزايد، ويحول دون تخمين النطاق

### 3.2 دقة العملات

تُستخدم عملات المنصة وعملات الألعاب بموحّد دقة `DECIMAL(18,4)`، ويستخدم الجانب PHP عائلة دوال `bcmath` (bcadd/bcsub/bcmul/bcdiv/bccomp) لجميع حسابات المبالغ.

**الأسباب**: أرقام الفاصلة العائمة (float/double) بها أخطاء دقة، وهي غير مقبولة في السيناريوهات المالية. يضمن DECIMAL + bcmath الحساب الدقيق.

### 3.3 القفل التفاؤلي للمحفظة

```sql
UPDATE erik_user_wallet 
SET balance = balance + ?, version = version + 1 
WHERE user_id = ? AND version = ?
```

إعادة المحاولة تلقائيًا عند فشل التحديث (حتى 5 مرات).

**الأسباب**:
- الشحن والاستبدال والسحب في منصة الألعاب كلها قد تعمل على نفس المحفظة بشكل متزامن
- أداء القفل التشاؤمي (SELECT FOR UPDATE) ضعيف تحت التزامن العالي
- أداء القفل التفاؤلي أفضل بكثير من القفل التشاؤمي في السيناريوهات منخفضة التعارض

### 3.4 عملية مراجعة السحب

```
المستخدم يبدأ السحب
  ├─ المفتاح العام مغلق → رفض
  ├─ المبلغ < عتبة المراجعة التلقائية → موافقة تلقائية
  └─ المبلغ >= العتبة → مراجعة بشرية → موافقة/رفض (عند الرفض تُعاد عملات المنصة)
```

**الأسباب**:
- المفتاح العام يُستخدم للتحكم في المخاطر الطارئة (مثل اكتشاف ثغرات أو حركة مرور شاذة)
- الموافقة التلقائية للمبالغ الصغيرة تقلل تكلفة العمل اليدوي وتحسن تجربة المستخدم
- المراجعة اليدوية للمبالغ الكبيرة تمنع غسيل الأموال والاحتيال

### 3.5 نموذج فرق الاستبدال

لكل عملة لعبة `exchange_rate` مستقل (1 عملة منصة = X عملة لعبة) و`spread_pct` (نسبة عمولة المنصة %).

عند الشراء: عملات اللعبة المستلمة = عملات المنصة × سعر الصرف × (1 - نسبة العمولة %)
عند البيع: عملات المنصة المستلمة = عملات اللعبة ÷ سعر الصرف × (1 - نسبة العمولة %)

**الأسباب**:
- مصدر إيراد المنصة هو فرق الاستبدال، وليس الدفع داخل اللعبة
- سعر الصرف المستقل يدعم استراتيجيات تسعير مختلفة للألعاب المختلفة
- يمكن ضبط نسبة الفرق بمرونة لتحقيق تشغيل دقيق

## 4. البنية الأمنية

على أساس الدفاع المتعمق الحالي المكون من 18 طبقة، تُضاف طبقات حماية جديدة لمنصة الألعاب:

| المستوى | الإجراء | السبب |
|------|------|------|
| أمان التزامن | القفل التفاؤلي version للمحفظة | منع الخصم/الإيداع المكرر |
| أمان السحب | مفتاح عام + عتبة مبلغ + حدود يومية/شهرية + تحقق poster-php | حماية متعددة الطبقات، تقليل مخاطر الأموال |
| أمان الاستبدال | فصل الاستعلام عن التسعير عن التنفيذ، انتهاء صلاحية الاستعلام خلال 60 ثانية | منع المراجحة بسبب تقلب سعر الصرف |
| أمان الألعاب | التحقق من توقيع استدعاءات الطرف الثالث + قائمة IP بيضاء + الدفاع ضد replay attack | منع تزوير تسوية الألعاب |
| إدارة المخاطر | محرك القواعد (قائمة IP السوداء، إنذار المبالغ الكبيرة، الشذوذ في التكرار) | حظر المعاملات المشبوهة لحظيًا |

## 5. تصميم التدويل

### 5.1 كشف اللغة

```
دخول الطلب
  ↓
LanguageMiddleware (وسيطة عامة)
  ├── 1. رأس الطلب X-Language
  ├── 2. رأس Accept-Language (zh → zh-CN, en → en-US)
  └── 3. الافتراضي en-US
  ↓
TranslationService::setLocale($locale)
  ↓
الحصول على النص المترجم في Controller عبر دالة __() أو TranslationService::trans()
```

### 5.2 تخزين الترجمات

- يخزن جدول قاعدة البيانات `erik_translation` جميع نصوص الترجمة (group + key + lang_code + value)
- في الطلب الأول تُحمَّل جميع البيانات من قاعدة البيانات إلى Redis (المفتاح: `i18n:translations`، TTL: ساعة واحدة)
- تقرأ الطلبات اللاحقة مباشرة من Redis، مع تسريع عبر التخزين المؤقت في الذاكرة
- يمكن توسيع لوحة إدارة الترجمات في الخلفية (يُنفَّذ في الإصدار الكامل)

### 5.3 تسمية مفاتيح الترجمة

الصيغة: `group.key` مثل `auth.login_success` و`wallet.insufficient_balance`

| المجموعة | المجال |
|------|------|
| auth | متعلق بالمصادقة |
| wallet | متعلق بالمحفظة |
| exchange | متعلق بالاستبدال |
| withdraw | متعلق بالسحب |
| deposit | متعلق بالشحن |
| game | متعلق بالألعاب |
| admin | لوحة الإدارة |
| error | رسائل الأخطاء |

### 5.4 استراتيجية التراجع

- توجد ترجمة بلغة الطلب → استخدامها
- لا توجد ترجمة بلغة الطلب → التراجع إلى en-US
- لا توجد حتى في en-US → إرجاع المفتاح الأصلي

### 5.5 تدويل الواجهة الأمامية

- يستخدم Flutter `AppTranslations` المبنية ذاتيًا + `LocaleController` (GetX)
- تُحفظ تفضيلات اللغة في SharedPreferences
- عند تبديل اللغة يُفعَّل إعادة عرض الواجهة العامة عبر `Get.updateLocale()`
- تستخدم فئة `StringResult` دالة Dart `toString()` لتحقيق صيغة الإدراج الطبيعية: `Text('${AppTranslations.t("key")}')`

## 6. تصاميم الإصدار القياسي الجديدة

### 6.1 محرك إدارة المخاطر

قبل العمليات المالية الحرجة يُنفَّذ فحص قواعد متعدد الطبقات:

```
طلب الشحن/السحب/الاستبدال
  ↓
RiskService::check(userId, type, context)
  ├── فحص قائمة IP السوداء (ip_blacklist) → block
  ├── فحص شذوذ المبالغ الكبيرة (amount_anomaly) → warn
  ├── فحص التكرار (frequency) → warn/block
  └── فحص السرعة (velocity) → block
  ↓
passed → تنفيذ عادي
warn   → تسجيل السجل، متابعة التنفيذ
block  → رفض العملية
```

تُخزَّن القواعد في جدول `erik_risk_rule`، والتهيئة بصيغة JSON، ويمكن ضبط العتبات والإجراءات ديناميكيًا.

### 6.2 التحقق من الهوية KYC

نظام تحقق ثلاثي المستويات:
- `default` — غير مُتحقَّق، حدود أساسية
- `verified` — اجتاز مراجعة KYC، حدود أعلى + رسوم أقل
- `vip` — مستوى VIP، أعلى الحدود + بدون رسوم

عملية التحقق:
```
يقدم المستخدم معلومات الوثائق → status=pending
مراجعة المشرف → approve/reject
approve → ترقية المستخدم تلقائيًا إلى مستوى verified
reject → يمكن للمستخدم إعادة التقديم
```

### 6.3 تسجيل دخول OAuth بطرف ثالث

دعم تسجيل دخول Google / Facebook / Apple:

```
النقر على زر OAuth في الواجهة الأمامية
  → GET /api/auth/oauth/{provider} → الحصول على عنوان التفويض
  → الانتقال إلى صفحة تفويض الطرف الثالث → موافقة المستخدم
  → الاستدعاء POST /api/auth/oauth/{provider}/callback
  → العثور على ربط موجود → تسجيل دخول مباشر
  → لا يوجد ربط → تسجيل مستخدم جديد تلقائيًا + ربط + إنشاء محفظة
```

### 6.4 استدعاء الدفع

```
اكتمال الدفع عبر الطرف الثالث → POST /api/payment/callback
  → التحقق من القائمة البيضاء للمزود (stripe/paypal فقط)
  → التحقق من التوقيع fail-closed (بدون secret/webhook_id، فشل التحقق، تجاوز فرق الطابع الزمني ±300 ثانية — يُرفض كل ذلك)
  → مطابقة مبلغ الاستدعاء مع مبلغ الطلب عبر bccomp (منع انتحال القنوات المتقاطعة)
  → تحديث حالة الطلب confirmed (معاملاتي، تراجع الإيداع عند الفشل)
  → إيداع عبر UserWallet::addBalance
  → تسجيل Transaction
  → فحص المخاطر عبر RiskService::check
```

### 6.5 حدود السحب المتدرجة

تُطبَّق حدود ورسوم مختلفة حسب مستوى KYC للمستخدم:

| المستوى | الحد الأقصى للعملية الواحدة | الحد اليومي | الحد الشهري | الرسوم |
|------|---------|--------|--------|--------|
| default | 1,000 | 10,000 | 50,000 | 1.00% |
| verified | 5,000 | 50,000 | 200,000 | 0.50% |
| vip | 20,000 | 200,000 | 1,000,000 | 0.00% |

## 7. تصميم قابلية التوسع

### 5.1 التوسع الأفقي

يدعم كل من admin/ وservice/ عمليات متعددة للعمال. مع وكيل عكسي Nginx، يمكن نشر عدة أجهزة لتحقيق التوسع الأفقي:

```
Nginx (موازنة الحمل)
  ├── admin-1 (:8787)
  ├── admin-2 (:8787)
  ├── service-1 (:8788)
  └── service-2 (:8788)
```

### 5.2 مسار تقسيم الوحدات

عندما يصبح service/ الواحد عنق زجاجة، يُقسَّم وفق المسار التالي:

```
service/ (متجانسة)
  → service-user/ (خدمة المستخدمين :8788)
  → service-wallet/ (خدمة المحافظ :8789)
  → service-game/ (خدمة الألعاب :8790)
  → service-payment/ (خدمة الدفع :8791)
```

معايير توقيت التقسيم:
- يتجاوز QPS لوحدة واحدة قدرة استيعاب الجهاز الواحد
- تحتاج وحدة معينة إلى حزمة تقنيات مستقلة أو استراتيجية نشر مستقلة
- يتوسع حجم الفريق إلى درجة الحاجة للتطوير المتوازي لوحدات مختلفة
