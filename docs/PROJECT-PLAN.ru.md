## I. Текущее состояние проекта

**Глобальная игровая агрегационная платформа** — PHP 8.3 + webman v2, monorepo из двух приложений:
`admin/` (8787, админ-панель) + `service/` (8788, C-сторона) + `apps/` (Flutter + HarmonyOS) + `install/` (установщик, 43 таблицы).

| Измерение | Фактический масштаб |
|------|---------|
| Контроллеры | admin 32 + service 30 = 62 |
| API-эндпоинты | ~149 (admin 103 / service 88, включая колбэки Webhook/Provider) |
| Модели данных | admin 46 / service 44, admin/service **дублируются** (нет общего слоя) |
| Тесты | 132 кейса / 8 файлов (проект admin), у service **ноль тестов** |
| Версия | v1.1 (2026-08-07): Redis-плагин, аналитические сервисы, деградация Redis, исправления тестов |

Реализованные возможности: JWT+RBAC, оптимистичная блокировка кошелька, пополнение (проверка подписи Stripe/PayPal), спред при обмене, проверка вывода + выплата через PayPal, CRUD игр/шлюз Provider (HMAC), купоны/VIP/достижения/тикеты/реферальные комиссии/2FA/соцчасть (друзья/чат WS)/турниры/Webhook/пуши (FCM/APNs/Huawei)/i18n на двух языках.

## II. Проблемы и риски (проверены экспериментально)

### CRITICAL — безопасность средств

| # | Проблема | Место |
|---|------|------|
| C1 | Платёжный колбэк: `provider` передаётся клиентом, при значении не stripe/paypal **проверка подписи полностью пропускается**, подделанный колбэк напрямую зачисляет средства | service/.../PaymentController.php:36-42 |
| C2 | Fail-open при проверке подписи: `STRIPE_WEBHOOK_SECRET` не настроен → `return true`; любое исключение PayPal → `return true`. Цепочка атаки: свой пополнительный ордер → подделанный колбэк → бесконечное пополнение | PaymentController.php:167, 225 |
| C3 | `JWT_SECRET_KEY` по умолчанию откатывается на публичный захардкоженный ключ `open-admin-jwt-secret-change-in-production`; без env в проде можно подделать admin-токен | admin+service config/plugin/erikwang2013/jwt/jwt.php:12 |

### HIGH — корректность/консистентность

| # | Проблема | Место |
|---|------|------|
| H1 | Аналитический сервис AnalyticsController: все 12 методов реализованы, но **ноль маршрутов** — мёртвый код 404, при этом VERSIONS.md заявляет о готовности | admin/config/route.php (0 упоминаний analytics) |
| H2 | Разрыв шины событий: emit вызывается в 4 местах (game.played/withdraw.completed/exchange.completed/referral.applied), `subscribe()` не зарегистрирован ни в одном процессе — события теряются сразу после публикации; движки VIP/достижений/уведомлений висят в воздухе | admin+service app/event/EventBus.php |
| H3 | common/ и model/ продублированы и разошлись (DepositLogService в двух разных версиях, User.php не совпадает); исправление в одном месте требует двойной работы. **common/service уже вынесен** в `packages/platform-common` (erik/platform-common, бывший common-php влит); модели и обёртки app/common по-прежнему в двух копиях | admin/common vs service/common → packages/platform-common |
| H4 | ~~HarmonyOS C-сторона `apps/harmonyos/` — пустой каталог, 0 страниц при заявленных в VERSIONS.md 5~~ — реализовано (2026-08-18: 5 страниц в `apps/harmonyos/`) | apps/harmonyos/ |
| H5 | Колбэк Stripe не проверяет допуск по таймстампу `t=` (возможен реплей), а зачисляемая сумма не сверяется с реально оплаченной в шлюзе | PaymentController.php:191-194 |
| H6 | Apple id_token лишь base64-декодирует payload без проверки подписи и aud/iss/exp — риск подмены идентичности между приложениями | OAuthController.php:376-380 |

### MEDIUM — надёжность/дефекты реализации

| # | Проблема |
|---|------|
| M1 | Двойной дефект 2FA: `/api/2fa/verify` публичен и не имеет блокировки попыток по пользователю (оракул для брутфорса); TOTP использует строку Base32 напрямую как HMAC-ключ (без декодирования) — не совпадает с Authenticator → **2FA фактически не работает** |
| M2 | Проверка/выплата вывода — check-then-act без атомарного обновления статуса; конкурентные запросы могут выплатить дважды; нет двойной проверки |
| M3 | URL колбэка Webhook проверяется только через filter_var — можно указать внутренний IP (SSRF); dispatch POST на произвольный URL |
| M4 | Дневные/месячные лимиты вывода «сначала запрос, потом вставка» — не атомарно, конкурентные запросы пробивают лимит |
| M5 | При сбое Redis нет единой абстракции fail-open: аннулирование JWT-чёрного списка и лимиты молча отключаются; пробелы деградации: PayoutService::getAccessToken, ChatWebSocket brpop, хранение OAuth state |
| M6 | ClickHouse не используется: вычисление вероятностей — на деле реальный COUNT(DISTINCT)+JOIN в MySQL, риск O(n²) на больших таблицах; composer-зависимость без отдачи |
| M7 | Незавершённая очередь: в admin/app/queue есть ComputeDailyStats + 3 ES-задачи, но webman/queue не установлен, в process.php не зарегистрированы — у всего нет вызывающих |
| M8 | Мёртвый код: сервисы Vip/Achievement/Notification/FeatureFlag без вызывающих; `DepositLogService::log()` — пустая реализация; остатки модели Test; грубый расчёт удержания по одной когорте |

### LOW
- Вывод возможен без принудительной 2FA/KYC на любой PayPal-email; примечание проверки попадает в текст уведомления (поверхность XSS)
- Документация расходится с фактом: install.sql 43 таблицы против написанных в документах 52; docker-compose 7 сервисов против 8 в FEATURES.md; «общие Model 34» неверно (admin 46 / service 44 по одной копии, общего слоя нет). CHANGELOG дополнен, см. `docs/CHANGELOG.md`.

### Пройденные пункты (подтверждено проверкой безопасности)
Оптимистичная блокировка кошелька + условное обновление по версии корректны; идемпотентность колбэков через условное обновление `where status=pending` корректна; везде ORM без прямой склейки SQL; .env не в git; все маршруты admin под AdminAuth+RBAC с отказом по умолчанию; проверка OAuth state + однократное потребление корректны.

> **Статус исправлений на 2026-08-18**: C1/C2/C3/H1/H5/H6 исправлены; H2 — шина событий: `process.php` регистрирует `event-consumer`, класс-потребитель `EventConsumer` реализован, у emit есть потребитель; M1 Base32 + блокировка по пользователю исправлены; M2 атомарность статуса вывода + опциональная двойная проверка сделаны; M3 SSRF Webhook заблокирован; M4 Redis-блокировка пользователя при заявке на вывод сделана; M5 частично (RateLimit fail-closed); P2-19 бизнес-метрики + канареечный FeatureFlag реализованы. Список проблем сохранён как историческое заключение аудита.
