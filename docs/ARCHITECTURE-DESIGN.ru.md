## 1. Цели проектирования

Построить глобальную универсальную интернационализированную игровую агрегационную платформу. Ключевые требования:

- Пользователь может пополнять счёт, обменивать средства на игровую валюту, играть, зарабатывать игровую валюту и выводить её
- Платформа единообразно управляет множеством игр (саморазработка + третьи стороны), у каждой игры своя валюта и курс
- Админ-панель предоставляет полные возможности проверки, переключателей и риск-контроля
- Поддержка мультиязычной, мультивалютной глобальной эксплуатации с несколькими платёжными каналами

## 2. Выбор архитектуры

### 2.1 Почему модульный монолит, а не микросервисы?

На текущем этапе выбран модульный монолит (Modular Monolith):

| Критерий | Модульный монолит | Микросервисы |
|------|----------|--------|
| Скорость разработки | Вызовы в одном процессе, без RPC | Нужно учитывать сетевые задержки, сериализацию |
| Согласованность транзакций | Локальные транзакции БД | Распределённые транзакции (сложно) |
| Сложность эксплуатации | Развёртывание одного процесса | Оркестрация множества сервисов, service discovery |
| Масштабируемость | В будущем можно разделить по модулям на микросервисы | Естественная независимая масштабируемость |
| Размер команды | Подходит для малой команды (1-5 человек) | Подходит для параллельной работы нескольких команд |

**Решение**: admin/ (админ-панель) и service/ (C-сторонний бизнес) — два независимых экземпляра webman, могут размещаться на одной машине (разные порты) или раздельно. Общий слой common/ через PSR-4 autoload устраняет дублирование кода. При росте нагрузки service/ можно разделить на несколько микросервисов (пользовательский, кошелёчный, игровой).

### 2.2 Почему webman v2, а не традиционный PHP-FPM?

| Критерий | webman v2 | PHP-FPM (Laravel) |
|------|-----------|-------------------|
| Производительность | Постоянно в памяти, поддержка корутин | Каждый запрос загружает все файлы |
| Конкурентность | Десятки тысяч QPS на одной машине | Сотни QPS на одной машине |
| Развёртывание | Просто, один процесс с несколькими worker | Сложная конфигурация Nginx + PHP-FPM |
| Экосистема | Совместим с компонентами Laravel Illuminate | Полная экосистема |

**Решение**: игровой платформе нужны высоконагруженные колбэки пополнений, запросы обмена и игровые расчёты; постоянно живущий в памяти webman с высокой конкурентностью подходит лучше. При этом совместимость с ORM, Queue и другими компонентами Laravel не уступает традиционным фреймворкам по скорости разработки.

### 2.3 Почему Flutter Web в стиле PC?

- Один код компилируется сразу под Web (PC), iOS, Android, HarmonyOS
- Зрелая библиотека компонентов Material 3, раскладка в стиле PC «боковая панель + верхняя панель» из коробки
- Общий слой бизнес-логики с клиентом HarmonyOS
- Отсутствие необходимости поддерживать две фронтенд-базы (React/Vue + Flutter)

## 3. Ключевые технические решения

### 3.1 Система ID

```
Snowflake 生成 BIGINT（内部分布式唯一）
    ↓
Hashids 编码为短字符串（对外不可逆推真实ID）
    ↓
API 请求/响应中传输 hashid 字符串
```

**Причины**:
- Snowflake глобально уникален, трендово возрастает — хорошо для индексов, не раскрывает объём бизнеса
- Hashids не даёт внешним через автоинкрементные ID перебирать данные и оценивать масштаб

### 3.2 Точность валют

Платформенная и игровая валюты единообразно используют точность `DECIMAL(18,4)`, все денежные расчёты на PHP — через семейство функций `bcmath` (bcadd/bcsub/bcmul/bcdiv/bccomp).

**Причины**: числа с плавающей точкой (float/double) имеют погрешность, неприемлемую в финансовых сценариях. DECIMAL + bcmath гарантируют точные вычисления.

### 3.3 Оптимистичная блокировка кошелька

```sql
UPDATE game_user_wallet 
SET balance = balance + ?, version = version + 1 
WHERE user_id = ? AND version = ?
```

При неудачном обновлении — автоматический повтор (до 5 раз).

**Причины**:
- Пополнение, обмен и вывод на игровой платформе могут конкурентно работать с одним кошельком
- Пессимистичная блокировка (SELECT FOR UPDATE) при высокой конкурентности работает плохо
- Оптимистичная блокировка при низкой частоте конфликтов значительно быстрее пессимистичной

### 3.4 Процесс проверки вывода

```
用户发起提现
  ├─ 全局开关关闭 → 拒绝
  ├─ 金额 < 自动审核阈值 → 自动通过
  └─ 金额 >= 阈值 → 人工审核 → 通过/拒绝（拒绝退回平台币）
```

**Причины**:
- Глобальный переключатель — для экстренного риск-контроля (обнаружение уязвимостей, аномального трафика)
- Автопропуск малых сумм снижает трудозатраты и улучшает пользовательский опыт
- Ручная проверка крупных сумм предотвращает отмывание денег и мошенничество

### 3.5 Модель спреда при обмене

У каждой игровой валюты свои `exchange_rate` (1 платформенная = X игровых) и `spread_pct` (комиссия платформы %).

При покупке: зачисление игровой валюты = платформенная × курс × (1 - комиссия%)
При продаже: зачисление платформенной = игровая ÷ курс × (1 - комиссия%)

**Причины**:
- Доход платформы — от спреда при обмене, а не от внутриигровых платежей
- Независимые курсы поддерживают разные ценовые стратегии игр
- Процент спреда гибко настраивается для тонкого управления

## 4. Архитектура безопасности

Поверх существующей 18-уровневой эшелонированной защиты для игровой платформы добавляются слои защиты:

| Слой | Меры | Причина |
|------|------|------|
| Безопасность параллелизма | Оптимистичная блокировка version кошелька | Защита от повторного списания/зачисления |
| Безопасность вывода | Глобальный переключатель + порог суммы + дневные/месячные лимиты + проверка poster-php | Многослойная защита, снижение денежных рисков |
| Безопасность обмена | Разделение котировки и сделки, котировка истекает за 60с | Защита от арбитража на колебаниях курса |
| Безопасность игр | Проверка подписи колбэков третьих сторон + IP-белые списки + защита от replay attack | Защита от подделки игровых расчётов |
| Риск-контроль | Движок правил (IP-чёрные списки, предупреждения о крупных суммах, аномальная частота) | Блокировка подозрительных транзакций в реальном времени |

## 5. Дизайн интернационализации

### 5.1 Определение языка

```
请求进入
  ↓
LanguageMiddleware（全局中间件）
  ├── 1. X-Language 请求头
  ├── 2. Accept-Language 头（zh → zh-CN, en → en-US）
  └── 3. 默认 en-US
  ↓
TranslationService::setLocale($locale)
  ↓
Controller 中 __() 函数或 TranslationService::trans() 获取翻译文本
```

### 5.2 Хранение переводов

- Таблица БД `game_translation` хранит все переводы (group + key + lang_code + value)
- При первом запросе всё грузится из БД в Redis (key: `i18n:translations`, TTL: 1 час)
- Последующие запросы читают прямо из Redis, ускорение через кэш в памяти
- В админке можно расширить страницу управления переводами (реализация в полной версии)

### 5.3 Именование ключей переводов

Формат: `group.key`, напр. `auth.login_success`, `wallet.insufficient_balance`

| Группа | Домен |
|------|------|
| auth | аутентификация |
| wallet | кошелёк |
| exchange | обмен |
| withdraw | вывод средств |
| deposit | пополнение |
| game | игры |
| admin | админ-панель |
| error | сообщения об ошибках |

### 5.4 Стратегия отката

- Для языка запроса есть перевод → использовать
- Для языка запроса нет перевода → откат на en-US
- Нет и в en-US → вернуть исходный key

### 5.5 Фронтенд i18n

- Flutter использует собственный `AppTranslations` + `LocaleController` (GetX)
- Предпочтение языка сохраняется в SharedPreferences
- При смене языка `Get.updateLocale()` запускает глобальный перерендер UI
- Класс `StringResult` через `toString()` в Dart даёт естественный инлайн-синтаксис: `Text('${AppTranslations.t("key")}')`

## 6. Новый дизайн стандартной версии

### 6.1 Движок риск-контроля

Перед ключевыми денежными операциями выполняется многослойная проверка правил:

```
充值/提现/兑换请求
  ↓
RiskService::check(userId, type, context)
  ├── IP 黑名单检测 (ip_blacklist) → block
  ├── 大额异常检测 (amount_anomaly) → warn
  ├── 频率检测 (frequency) → warn/block
  └── 速度检测 (velocity) → block
  ↓
passed → 正常执行
warn   → 记录日志，继续执行
block  → 拒绝操作
```

Правила хранятся в таблице `game_risk_rule`, конфигурация в JSON, пороги и действия настраиваются динамически.

### 6.2 KYC-верификация

Трёхуровневая система:
- `default` — не верифицирован, базовые лимиты
- `verified` — KYC пройден, повышенные лимиты + сниженная комиссия
- `vip` — уровень VIP, максимальные лимиты + нулевая комиссия

Процесс верификации:
```
用户提交证件信息 → status=pending
管理员审核 → approve/reject
approve → 用户自动升级为 verified 等级
reject → 用户可重新提交
```

### 6.3 OAuth-вход через третьи стороны

Поддержка входа Google / Facebook / Apple:

```
前端点击 OAuth 按钮
  → GET /api/auth/oauth/{provider} → 获取授权URL
  → 跳转第三方授权页 → 用户同意
  → 回调 POST /api/auth/oauth/{provider}/callback
  → 查找已有绑定 → 直接登录
  → 无绑定 → 自动注册新用户 + 绑定 + 创建钱包
```

### 6.4 Платёжный колбэк

```
第三方支付完成 → POST /api/payment/callback
  → provider 白名单校验（仅 stripe/paypal）
  → 验签 fail-closed（未配 secret/webhook_id、验签失败、时间戳超 ±300s 一律拒绝）
  → 回调金额与订单金额 bccomp 核对（防跨渠道冒用）
  → 更新订单状态 confirmed（事务化，入账失败回滚）
  → UserWallet::addBalance 到账
  → 记录 Transaction
  → RiskService::check 风控检查
```

### 6.5 Ступенчатые лимиты вывода

По уровню KYC пользователя применяются разные лимиты и комиссии:

| Уровень | Лимит одной операции | Дневной лимит | Месячный лимит | Комиссия |
|------|---------|--------|--------|--------|
| default | 1,000 | 10,000 | 50,000 | 1.00% |
| verified | 5,000 | 50,000 | 200,000 | 0.50% |
| vip | 20,000 | 200,000 | 1,000,000 | 0.00% |

## 7. Дизайн расширяемости

### 5.1 Горизонтальное расширение

admin/ и service/ поддерживают несколько worker-процессов. Вместе с Nginx reverse proxy можно разворачивать на нескольких машинах:

```
Nginx (负载均衡)
  ├── admin-1 (:8787)
  ├── admin-2 (:8787)
  ├── service-1 (:8788)
  └── service-2 (:8788)
```

### 5.2 Путь разбиения на модули

Когда единый service/ становится узким местом, разбиение идёт по следующему пути:

```
service/ (单体)
  → service-user/ (用户服务 :8788)
  → service-wallet/ (钱包服务 :8789)
  → service-game/ (游戏服务 :8790)
  → service-payment/ (支付服务 :8791)
```

Критерии момента разбиения:
- QPS одного модуля превышает возможности одной машины
- Модулю нужен отдельный технологический стек или стратегия развёртывания
- Команда выросла настолько, что требуется параллельная разработка разных модулей
