## 1. ডিজাইন লক্ষ্য

বিশ্বব্যাপী সাধারণ-উদ্দেশ্য, আন্তর্জাতিক গেম অ্যাগ্রিগেশন প্ল্যাটফর্ম নির্মাণ। মূল প্রয়োজন:

- ব্যবহারকারী প্ল্যাটফর্মে টপ-আপ, গেম কয়েনে বিনিময়, গেম খেলা, গেম কয়েন অর্জন ও উত্তোলন করতে পারবে
- প্ল্যাটফর্ম একাধিক গেম (নিজস্ব + থার্ড-পার্টি) সমন্বিতভাবে পরিচালনা করে, প্রতিটি গেমের আলাদা গেম কয়েন ও বিনিময় হার আছে
- ব্যাকএন্ড সম্পূর্ণ রিভিউ, সুইচ, রিস্ক কন্ট্রোল ক্ষমতা দেয়
- বহুভাষা, মাল্টি-কারেন্সি, মাল্টি-পেমেন্ট চ্যানেলের গ্লোবাল অপারেশন সাপোর্ট

## 2. আর্কিটেকচার নির্বাচন

### 2.1 কেন মডিউলার মনোলিথ, মাইক্রোসার্ভিস নয়?

বর্তমান পর্যায়ে মডিউলার মনোলিথ (Modular Monolith) নির্বাচন:

| বিবেচনা | মডিউলার মনোলিথ | মাইক্রোসার্ভিস |
|------|----------|--------|
| ডেভেলপমেন্ট দক্ষতা | একই প্রসেসে কল, RPC প্রয়োজন নেই | নেটওয়ার্ক লেটেন্সি, সিরিয়ালাইজেশন মোকাবেলা করতে হয় |
| ট্রানজেকশন সামঞ্জস্য | লোকাল ডেটাবেস ট্রানজেকশন | ডিস্ট্রিবিউটেড ট্রানজেকশন (জটিল) |
| অপারেশন জটিলতা | একক প্রসেস ডিপ্লয় | মাল্টি-সার্ভিস অর্কেস্ট্রেশন, সার্ভিস ডিসকভারি |
| স্কেলেবিলিটি | ভবিষ্যতে মডিউল অনুযায়ী মাইক্রোসার্ভিসে বিভক্ত করা যায় | স্বাভাবিকভাবে স্বাধীন স্কেলিং |
| টিম সাইজ | ছোট টিমের জন্য উপযুক্ত (১-৫ জন) | একাধিক টিম সমান্তরাল ডেভেলপমেন্টের জন্য উপযুক্ত |

**সিদ্ধান্ত**: admin/ (অ্যাডমিন প্যানেল) এবং service/ (C-এন্ড ব্যবসা) দুটি স্বাধীন webman ইনস্ট্যান্স, একই মেশিনে (আলাদা পোর্টে) বা আলাদাভাবে ডিপ্লয় করা যায়। শেয়ার্ড লেয়ার common/ PSR-4 autoload দিয়ে কোড ডুপ্লিকেশন দূর করে। ভবিষ্যতে ব্যবসার পরিমাণ বাড়লে service/ একাধিক মাইক্রোসার্ভিসে বিভক্ত করা যাবে (ইউজার সার্ভিস, ওয়ালেট সার্ভিস, গেম সার্ভিস)।

### 2.2 কেন ঐতিহ্যবাহী PHP-FPM-এর বদলে webman v2?

| বিবেচনা | webman v2 | PHP-FPM (Laravel) |
|------|-----------|-------------------|
| পারফরম্যান্স | স্থায়ী মেমরি, কো-রুটিন সাপোর্ট | প্রতিটি রিকোয়েস্টে সব ফাইল লোড |
| কনকারেন্সি | একক মেশিনে কয়েক হাজার QPS | একক মেশিনে কয়েকশ QPS |
| ডিপ্লয় | সহজ, এক প্রসেস মাল্টি-ওয়ার্কার | Nginx + PHP-FPM কনফিগ জটিল |
| ইকোসিস্টেম | Laravel Illuminate কম্পোনেন্ট সামঞ্জস্যপূর্ণ | সম্পূর্ণ ইকোসিস্টেম |

**সিদ্ধান্ত**: গেম প্ল্যাটফর্মে উচ্চ কনকারেন্সির টপ-আপ কলব্যাক, বিনিময় রিকোয়েস্ট, গেম সেটেলমেন্ট প্রক্রিয়া করতে হয়; webman-এর স্থায়ী মেমরি ও উচ্চ কনকারেন্সি ক্ষমতা বেশি উপযুক্ত। একই সাথে Laravel-এর ORM, Queue ইত্যাদি কম্পোনেন্ট সামঞ্জস্যপূর্ণ, ডেভেলপমেন্ট দক্ষতা ঐতিহ্যবাহী ফ্রেমওয়ার্কের চেয়ে কম নয়।

### 2.3 কেন Flutter Web PC শৈলী?

- একটি কোডবেস একই সাথে Web (PC), iOS, Android, HarmonyOS-এ কম্পাইল করা যায়

- React/Vue + Flutter দুই সেট ফ্রন্টএন্ড কোড রক্ষণাবেক্ষণ এড়ায়

## 3. মূল প্রযুক্তিগত সিদ্ধান্ত

### 3.1 ID সিস্টেম

```
Snowflake 生成 BIGINT（内部分布式唯一）
    ↓
Hashids 编码为短字符串（对外不可逆推真实ID）
    ↓
API 请求/响应中传输 hashid 字符串
```

**কারণ**:
- Snowflake গ্লোবালি ইউনিক, ট্রেন্ড-ইনক্রিমেন্টাল হওয়ায় ইনডেক্সের জন্য ভালো, ব্যবসার পরিমাণ প্রকাশ করে না
- Hashids বাইরের পক্ষকে অটো-ইনক্রিমেন্ট ID দিয়ে ডেটা ঘুরে দেখা ও আকার অনুমান করা থেকে আটকায়

### 3.2 কয়েন নির্ভুলতা

প্ল্যাটফর্ম কয়েন ও গেম কয়েন উভয়েই `DECIMAL(18,4)` নির্ভুলতা ব্যবহার করে, PHP পাশে সব অর্থের হিসাব `bcmath` ফাংশন পরিবার (bcadd/bcsub/bcmul/bcdiv/bccomp) দিয়ে করা হয়।

**কারণ**: ফ্লোট (float/double) সংখ্যায় নির্ভুলতা ত্রুটি থাকে, যা ফাইন্যান্সিয়াল পরিস্থিতিতে গ্রহণযোগ্য নয়। DECIMAL + bcmath সঠিক গণনা নিশ্চিত করে।

### 3.3 ওয়ালেট অপটিমিস্টিক লক

```sql
UPDATE erik_user_wallet 
SET balance = balance + ?, version = version + 1 
WHERE user_id = ? AND version = ?
```

আপডেট ব্যর্থ হলে স্বয়ংক্রিয় রিট্রাই (সর্বোচ্চ ৫ বার)।

**কারণ**:
- গেম প্ল্যাটফর্মে টপ-আপ, বিনিময়, উত্তোলন একই ওয়ালেটে কনকারেন্ট অপারেশন হতে পারে
- পেসিমিস্টিক লক (SELECT FOR UPDATE) উচ্চ কনকারেন্সিতে পারফরম্যান্স খারাপ
- অপটিমিস্টিক লক কনফ্লিক্ট রেট কম এমন পরিস্থিতিতে পেসিমিস্টিক লকের চেয়ে অনেক ভালো পারফরম্যান্স দেয়

### 3.4 উত্তোলন রিভিউ প্রক্রিয়া

```
用户发起提现
  ├─ 全局开关关闭 → 拒绝
  ├─ 金额 < 自动审核阈值 → 自动通过
  └─ 金额 >= 阈值 → 人工审核 → 通过/拒绝（拒绝退回平台币）
```

**কারণ**:
- গ্লোবাল সুইচ জরুরি রিস্ক কন্ট্রোলের জন্য (দুর্বলতা আবিষ্কার, অস্বাভাবিক ট্রাফিক ইত্যাদি)
- ছোট অঙ্ক স্বয়ংক্রিয় পাস মানব খরচ কমায়, ইউজার এক্সপেরিয়েন্স বাড়ায়
- বড় অঙ্কে মানব রিভিউ মানি লন্ডারিং ও জালিয়াতি প্রতিরোধ করে

### 3.5 বিনিময় স্প্রেড মডেল

প্রতিটি গেম কয়েনের আলাদা `exchange_rate` (১ প্ল্যাটফর্ম কয়েন = X গেম কয়েন) এবং `spread_pct` (প্ল্যাটফর্ম কমিশন %)।

বাই করলে: গেম কয়েন ক্রেডিট = প্ল্যাটফর্ম কয়েন × রেট × (১ - কমিশন%)
সেল করলে: প্ল্যাটফর্ম কয়েন ক্রেডিট = গেম কয়েন ÷ রেট × (১ - কমিশন%)

**কারণ**:
- প্ল্যাটফর্মের আয় বিনিময় স্প্রেড থেকে আসে, গেমের ভেতরের পেমেন্ট থেকে নয়
- স্বাধীন রেট আলাদা গেমের প্রাইসিং কৌশল সাপোর্ট করে
- স্প্রেড অনুপাত নমনীয়ভাবে সামঞ্জস্য করা যায়, সূক্ষ্ম অপারেশনাল কন্ট্রোল সম্ভব

## 4. নিরাপত্তা আর্কিটেকচার

বিদ্যমান ১৮ স্তর গভীর প্রতিরক্ষার ভিত্তিতে গেম প্ল্যাটফর্মের জন্য নতুন সুরক্ষা স্তর:

| স্তর | ব্যবস্থা | কারণ |
|------|------|------|
| কনকারেন্সি নিরাপত্তা | ওয়ালেট version অপটিমিস্টিক লক | ডুপ্লিকেট ডেবিট/ডুপ্লিকেট ক্রেডিট প্রতিরোধ |
| উত্তোলন নিরাপত্তা | গ্লোবাল সুইচ + অঙ্ক থ্রেশহোল্ড + দৈনিক/মাসিক সীমা + poster-php ভেরিফিকেশন | মাল্টি-লেয়ার প্রতিরোধ, ফান্ড ঝুঁকি কমানো |
| বিনিময় নিরাপত্তা | কোটেশন ও এক্সিকিউশন পৃথক, কোটেশন ৬০s মেয়াদোত্তীর্ণ | রেট ওঠানামায় আর্বিট্রেজ প্রতিরোধ |
| গেম নিরাপত্তা | থার্ড-পার্টি কলব্যাক সিগনেচার ভেরিফিকেশন + IP হোয়াইটলিস্ট + replay attack প্রতিরোধ | জাল গেম সেটেলমেন্ট প্রতিরোধ |
| রিস্ক কন্ট্রোল | রুল ইঞ্জিন (IP ব্ল্যাকলিস্ট, বড় অঙ্ক অ্যালার্ট, ফ্রিকোয়েন্সি অস্বাভাবিকতা) | সন্দেহজনক লেনদেন রিয়েল-টাইম ব্লক |

## 5. ইন্টারন্যাশনালাইজেশন ডিজাইন

### 5.1 ভাষা ডিটেকশন

```
请求进入
  ↓
LanguageMiddleware（全局中间件）
  ├── 1. X-Language 请求头
  ├── 2. Accept-Language 头（zh → zh-CN, en → en-US）
  └── 3. 默认 en-US
  ↓
TranslationService::setLocale($locale)
  ↓
Controller 中 __() 函数或 TranslationService::trans() 获取翻译文本
```

### 5.2 অনুবাদ স্টোরেজ

- ডেটাবেস টেবিল `erik_translation`-এ সব অনুবাদ টেক্সট সংরক্ষিত (group + key + lang_code + value)
- প্রথম রিকোয়েস্টে ডেটাবেস থেকে সম্পূর্ণ Redis-এ লোড (key: `i18n:translations`, TTL: ১ ঘণ্টা)
- পরবর্তী রিকোয়েস্ট সরাসরি Redis থেকে পড়ে, মেমরি ক্যাশ ত্বরান্বিত করে
- অ্যাডমিন প্যানেলে অনুবাদ ম্যানেজমেন্ট পেজ যোগ করা যায় (ফুল ভার্সনে বাস্তবায়িত)

### 5.3 অনুবাদ কী নামকরণ

ফরম্যাট: `group.key` যেমন `auth.login_success`, `wallet.insufficient_balance`

| গ্রুপ | ডোমেইন |
|------|------|
| auth | অথেনটিকেশন সম্পর্কিত |
| wallet | ওয়ালেট সম্পর্কিত |
| exchange | বিনিময় সম্পর্কিত |
| withdraw | উত্তোলন সম্পর্কিত |
| deposit | টপ-আপ সম্পর্কিত |
| game | গেম সম্পর্কিত |
| admin | অ্যাডমিন প্যানেল |
| error | ত্রুটি বার্তা |

### 5.4 ফলব্যাক কৌশল

- রিকোয়েস্ট ভাষায় অনুবাদ থাকলে → ব্যবহার
- রিকোয়েস্ট ভাষায় অনুবাদ না থাকলে → en-US-এ ফলব্যাক
- en-US-ও না থাকলে → আসল key রিটার্ন

### 5.5 ফ্রন্টএন্ড i18n

- Flutter নিজস্ব `AppTranslations` + `LocaleController` (GetX) ব্যবহার করে
- ভাষা পছন্দ SharedPreferences-এ পার্সিস্ট হয়
- ভাষা পরিবর্তনে `Get.updateLocale()` দিয়ে গ্লোবাল UI রি-রেন্ডার ট্রিগার
- `StringResult` ক্লাস Dart-এর `toString()` ব্যবহার করে প্রাকৃতিক ইনলাইন সিনট্যাক্স: `Text('${AppTranslations.t("key")}')`

## 6. স্ট্যান্ডার্ড সংস্করণে নতুন ডিজাইন

### 6.1 রিস্ক কন্ট্রোল ইঞ্জিন

মূল ফান্ড অপারেশনের আগে মাল্টি-লেয়ার রুল চেক:

```
充值/提现/兑换请求
  ↓
RiskService::check(userId, type, context)
  ├── IP 黑名单检测 (ip_blacklist) → block
  ├── 大额异常检测 (amount_anomaly) → warn
  ├── 频率检测 (frequency) → warn/block
  └── 速度检测 (velocity) → block
  ↓
passed → 正常执行
warn   → 记录日志，继续执行
block  → 拒绝操作
```

নিয়ম `erik_risk_rule` টেবিলে সংরক্ষিত, কনফিগ JSON আকারে, থ্রেশহোল্ড ও অ্যাকশন ডাইনামিকভাবে সামঞ্জস্য করা যায়।

### 6.2 KYC রিয়েল-নেম ভেরিফিকেশন

তিন-স্তরের ভেরিফিকেশন সিস্টেম:
- `default` — ভেরিফায়েড নয়, মৌলিক সীমা
- `verified` — KYC রিভিউ পাস, সীমা বেড়ে ফি কমে
- `vip` — VIP লেভেল, সর্বোচ্চ সীমা + শূন্য ফি

ভেরিফিকেশন প্রক্রিয়া:
```
用户提交证件信息 → status=pending
管理员审核 → approve/reject
approve → 用户自动升级为 verified 等级
reject → 用户可重新提交
```

### 6.3 OAuth থার্ড-পার্টি লগইন

Google / Facebook / Apple লগইন সাপোর্ট:

```
前端点击 OAuth 按钮
  → GET /api/auth/oauth/{provider} → 获取授权URL
  → 跳转第三方授权页 → 用户同意
  → 回调 POST /api/auth/oauth/{provider}/callback
  → 查找已有绑定 → 直接登录
  → 无绑定 → 自动注册新用户 + 绑定 + 创建钱包
```

### 6.4 পেমেন্ট কলব্যাক

```
第三方支付完成 → POST /api/payment/callback
  → provider 白名单校验（仅 stripe/paypal）
  → 验签 fail-closed（未配 secret/webhook_id、验签失败、时间戳超 ±300s 一律拒绝）
  → 回调金额与订单金额 bccomp 核对（防跨渠道冒用）
  → 更新订单状态 confirmed（事务化，入账失败回滚）
  → UserWallet::addBalance 到账
  → 记录 Transaction
  → RiskService::check 风控检查
```

### 6.5 লেভেলভিত্তিক উত্তোলন সীমা

ব্যবহারকারীর KYC লেভেল অনুযায়ী আলাদা সীমা ও ফি প্রয়োগ:

| লেভেল | প্রতি লেনদেন সর্বোচ্চ | দৈনিক সীমা | মাসিক সীমা | ফি |
|------|---------|--------|--------|--------|
| default | 1,000 | 10,000 | 50,000 | 1.00% |
| verified | 5,000 | 50,000 | 200,000 | 0.50% |
| vip | 20,000 | 200,000 | 1,000,000 | 0.00% |

## 7. স্কেলেবিলিটি ডিজাইন

### 5.1 হরাইজন্টাল স্কেলিং

admin/ ও service/ উভয়ই মাল্টি-ওয়ার্কার প্রসেস সাপোর্ট করে। Nginx রিভার্স প্রক্সির সাথে একাধিক মেশিনে ডিপ্লয় করে হরাইজন্টাল স্কেলিং:

```
Nginx (负载均衡)
  ├── admin-1 (:8787)
  ├── admin-2 (:8787)
  ├── service-1 (:8788)
  └── service-2 (:8788)
```

### 5.2 মডিউল বিভাজনের পথ

একক service/ বাধা হয়ে গেলে নিচের পথে বিভক্ত:

```
service/ (单体)
  → service-user/ (用户服务 :8788)
  → service-wallet/ (钱包服务 :8789)
  → service-game/ (游戏服务 :8790)
  → service-payment/ (支付服务 :8791)
```

বিভাজনের সময় নির্ধারণের মানদণ্ড:
- একক মডিউলের QPS একক মেশিনের ধারণক্ষমতা ছাড়ায়
- কোনো মডিউলের আলাদা টেক স্ট্যাক বা ডিপ্লয় কৌশল প্রয়োজন হয়
- টিম সাইজ এমন পর্যায়ে পৌঁছায় যে আলাদা মডিউল সমান্তরাল ডেভেলপমেন্ট প্রয়োজন
