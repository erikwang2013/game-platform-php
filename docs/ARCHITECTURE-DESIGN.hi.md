## 1. डिज़ाइन लक्ष्य

वैश्विक सार्वभौमिक, अंतर्राष्ट्रीयकृत गेम एग्रीगेशन प्लेटफ़ॉर्म का निर्माण। मुख्य आवश्यकताएँ:

- उपयोगकर्ता प्लेटफ़ॉर्म पर रिचार्ज, गेम कॉइन विनिमय, गेम खेलना, गेम कॉइन कमाना और निकासी कर सकते हैं
- प्लेटफ़ॉर्म एकीकृत रूप से कई गेम प्रबंधित करता है (स्वयं विकसित + तृतीय-पक्ष), प्रत्येक गेम की स्वतंत्र गेम कॉइन और विनिमय दर होती है
- बैकएंड पूर्ण समीक्षा, स्विच और जोखिम नियंत्रण क्षमताएँ प्रदान करता है
- बहुभाषा, बहु-मुद्रा, बहु-भुगतान चैनल के साथ वैश्विक संचालन समर्थन

## 2. आर्किटेक्चर चयन

### 2.1 माइक्रोसर्विस के बजाय मॉड्यूलर मोनोलिथ क्यों?

वर्तमान चरण में मॉड्यूलर मोनोलिथ चुना गया है:

| विचार | मॉड्यूलर मोनोलिथ | माइक्रोसर्विस |
|------|----------|--------|
| विकास दक्षता | एक ही प्रक्रिया में कॉल, RPC की आवश्यकता नहीं | नेटवर्क विलंब, क्रमबद्धता संभालनी पड़ती है |
| लेनदेन स्थिरता | स्थानीय डेटाबेस लेनदेन | वितरित लेनदेन (जटिल) |
| संचालन जटिलता | एकल प्रक्रिया तैनाती | बहु-सेवा ऑर्केस्ट्रेशन, सेवा खोज |
| स्केलेबिलिटी | भविष्य में मॉड्यूल-वार माइक्रोसर्विस में विभाजित किया जा सकता है | स्वाभाविक रूप से स्वतंत्र स्केलिंग समर्थित |
| टीम आकार | छोटी टीमों के लिए उपयुक्त (1-5 लोग) | बहु-टीम समानांतर विकास के लिए उपयुक्त |

**निर्णय**: admin/ (प्रशासन कंसोल) और service/ (C-छोर व्यवसाय) दो स्वतंत्र webman उदाहरण हैं, एक ही मशीन पर (अलग-अलग पोर्ट) या अलग-अलग तैनात किए जा सकते हैं। साझा परत common/ PSR-4 autoload के माध्यम से कोड दोहराव समाप्त करती है। भविष्य में व्यवसाय वृद्धि के बाद, service/ को कई माइक्रोसर्विस (उपयोगकर्ता सेवा, वॉलेट सेवा, गेम सेवा) में विभाजित किया जा सकता है।

### 2.2 पारंपरिक PHP-FPM के बजाय webman v2 क्यों?

| विचार | webman v2 | PHP-FPM (Laravel) |
|------|-----------|-------------------|
| प्रदर्शन | स्थायी मेमोरी, कोरूटीन समर्थन | प्रत्येक अनुरोध पर सभी फ़ाइलें लोड होती हैं |
| समवर्तीता | एकल मशीन पर हजारों QPS | एकल मशीन पर सैकड़ों QPS |
| तैनाती | सरल, एकल प्रक्रिया कई worker | Nginx + PHP-FPM कॉन्फ़िग जटिल |
| पारिस्थितिकी | Laravel Illuminate घटकों के साथ संगत | पूर्ण पारिस्थितिकी |

**निर्णय**: गेम प्लेटफ़ॉर्म को उच्च-समवर्ती रिचार्ज कॉलबैक, विनिमय अनुरोध और गेम निपटान संभालने की आवश्यकता है; webman की स्थायी मेमोरी और उच्च समवर्ती क्षमता अधिक उपयुक्त है। साथ ही Laravel के ORM, Queue आदि घटकों के साथ संगत होने से विकास दक्षता पारंपरिक फ्रेमवर्क से कम नहीं है।

### 2.3 Flutter Web PC शैली क्यों?

- एक ही कोड Web (PC), iOS, Android, HarmonyOS पर संकलित किया जा सकता है
- Material 3 घटक पुस्तकालय परिपक्व, PC शैली साइडबार+टॉपबार लेआउट आउट-ऑफ़-द-बॉक्स उपलब्ध
- HarmonyOS क्लाइंट के साथ व्यवसाय तर्क परत साझा करता है
- React/Vue + Flutter दो फ्रंटएंड कोड बनाए रखने से बचाता है

## 3. मुख्य तकनीकी निर्णय

### 3.1 ID प्रणाली

```
Snowflake BIGINT उत्पन्न करता है (आंतरिक रूप से वितरित रूप से अद्वितीय)
    ↓
Hashids छोटे स्ट्रिंग में एन्कोड करता है (बाहरी रूप से वास्तविक ID अनुमानित नहीं हो सकती)
    ↓
API अनुरोध/प्रतिक्रिया में hashid स्ट्रिंग प्रसारित होती है
```

**कारण**:
- Snowflake वैश्विक रूप से अद्वितीय, प्रवृत्ति-बढ़ती अनुक्रमित करने में लाभकारी, व्यवसाय मात्रा उजागर नहीं करता
- Hashids बाहरी लोगों को क्रमिक ID के माध्यम से डेटा ट्रैवर्स करने और पैमाने का अनुमान लगाने से रोकता है

### 3.2 मुद्रा सटीकता

प्लेटफ़ॉर्म कॉइन और गेम कॉइन दोनों `DECIMAL(18,4)` सटीकता का उपयोग करते हैं, PHP पक्ष सभी राशि गणनाओं के लिए `bcmath` फ़ंक्शन परिवार (bcadd/bcsub/bcmul/bcdiv/bccomp) का उपयोग करता है।

**कारण**: फ्लोटिंग-पॉइंट (float/double) में सटीकता त्रुटि होती है, जो वित्तीय परिदृश्यों में अस्वीकार्य है। DECIMAL + bcmath सटीक गणना सुनिश्चित करता है।

### 3.3 वॉलेट ऑप्टिमिस्टिक लॉक

```sql
UPDATE game_user_wallet 
SET balance = balance + ?, version = version + 1 
WHERE user_id = ? AND version = ?
```

अपडेट विफल होने पर स्वचालित पुनः प्रयास (अधिकतम 5 बार)।

**कारण**:
- गेम प्लेटफ़ॉर्म पर रिचार्ज, विनिमय और निकासी सभी एक ही वॉलेट पर समवर्ती रूप से संचालित हो सकते हैं
- पेसिमिस्टिक लॉक (SELECT FOR UPDATE) उच्च समवर्तीता में खराब प्रदर्शन करता है
- ऑप्टिमिस्टिक लॉक कम टकराव दर वाले परिदृश्यों में पेसिमिस्टिक लॉक से कहीं बेहतर प्रदर्शन करता है

### 3.4 निकासी समीक्षा प्रक्रिया

```
उपयोगकर्ता निकासी आरंभ करता है
  ├─ वैश्विक स्विच बंद → अस्वीकार
  ├─ राशि < स्वचालित समीक्षा सीमा → स्वचालित स्वीकृति
  └─ राशि >= सीमा → मैन्युअल समीक्षा → स्वीकृति/अस्वीकृति (अस्वीकृति पर प्लेटफ़ॉर्म कॉइन वापस)
```

**कारण**:
- वैश्विक स्विच आपातकालीन जोखिम नियंत्रण के लिए (जैसे भेद्यता खोज, असामान्य ट्रैफ़िक)
- छोटी राशि स्वचालित स्वीकृति मैन्युअल लागत घटाती है और उपयोगकर्ता अनुभव बेहतर करती है
- बड़ी राशि की मैन्युअल समीक्षा मनी लॉन्ड्रिंग और धोखाधड़ी रोकती है

### 3.5 विनिमय अंतर मॉडल

प्रत्येक गेम कॉइन की स्वतंत्र `exchange_rate` (1 प्लेटफ़ॉर्म कॉइन = X गेम कॉइन) और `spread_pct` (प्लेटफ़ॉर्म कमीशन%) होती है।

खरीदते समय: गेम कॉइन जमा = प्लेटफ़ॉर्म कॉइन × विनिमय दर × (1 - कमीशन%)
बेचते समय: प्लेटफ़ॉर्म कॉइन जमा = गेम कॉइन ÷ विनिमय दर × (1 - कमीशन%)

**कारण**:
- प्लेटफ़ॉर्म राजस्व विनिमय अंतर से आता है, न कि गेम के भीतर भुगतान से
- स्वतंत्र विनिमय दर विभिन्न गेम की मूल्य निर्धारण रणनीति का समर्थन करती है
- अंतर प्रतिशत लचीले ढंग से समायोजित किया जा सकता है, परिष्कृत संचालन प्राप्त करने के लिए

## 4. सुरक्षा आर्किटेक्चर

मौजूदा 18-परत गहन रक्षा के आधार पर, गेम प्लेटफ़ॉर्म के लिए नई सुरक्षा परतें:

| परत | उपाय | कारण |
|------|------|------|
| समवर्ती सुरक्षा | वॉलेट version ऑप्टिमिस्टिक लॉक | बार-बार कटौती/बार-बार जमा रोकता है |
| निकासी सुरक्षा | वैश्विक स्विच + राशि सीमा + दैनिक/मासिक सीमा + poster-php सत्यापन | बहु-परत रोकथाम, धन जोखिम घटाता है |
| विनिमय सुरक्षा | मूल्य पूछताछ और निष्पादन अलग, पूछताछ 60s में समाप्त | विनिमय दर उतार-चढ़ाव से आर्बिट्रेज रोकता है |
| गेम सुरक्षा | तृतीय-पक्ष कॉलबैक हस्ताक्षर सत्यापन + IP श्वेतसूची + replay attack सुरक्षा | नकली गेम निपटान रोकता है |
| जोखिम नियंत्रण | नियम इंजन (IP ब्लैकलिस्ट, बड़ी राशि अलर्ट, आवृत्ति असामान्यता) | संदिग्ध लेनदेन को वास्तविक समय में रोकता है |

## 5. अंतर्राष्ट्रीयकरण डिज़ाइन

### 5.1 भाषा पहचान

```
अनुरोध प्रवेश
  ↓
LanguageMiddleware (वैश्विक मिडलवेयर)
  ├── 1. X-Language अनुरोध हेडर
  ├── 2. Accept-Language हेडर (zh → zh-CN, en → en-US)
  └── 3. डिफ़ॉल्ट en-US
  ↓
TranslationService::setLocale($locale)
  ↓
Controller में __() फ़ंक्शन या TranslationService::trans() से अनुवाद पाठ प्राप्त करें
```

### 5.2 अनुवाद भंडारण

- डेटाबेस तालिका `game_translation` सभी अनुवाद पाठ संग्रहीत करती है (group + key + lang_code + value)
- पहला अनुरोध डेटाबेस से पूर्ण रूप से Redis में लोड होता है (key: `i18n:translations`, TTL: 1 घंटा)
- बाद के अनुरोध सीधे Redis से पढ़ते हैं, मेमोरी कैश गति बढ़ाता है
- प्रशासन कंसोल अनुवाद प्रबंधन पेज का विस्तार कर सकता है (पूर्ण संस्करण में कार्यान्वित)

### 5.3 अनुवाद कुंजी नामकरण

प्रारूप: `group.key` जैसे `auth.login_success`, `wallet.insufficient_balance`

| समूह | क्षेत्र |
|------|------|
| auth | प्रमाणीकरण संबंधित |
| wallet | वॉलेट संबंधित |
| exchange | विनिमय संबंधित |
| withdraw | निकासी संबंधित |
| deposit | रिचार्ज संबंधित |
| game | गेम संबंधित |
| admin | प्रशासन कंसोल |
| error | त्रुटि संदेश |

### 5.4 रोलबैक रणनीति

- अनुरोध भाषा में अनुवाद मौजूद → उपयोग करें
- अनुरोध भाषा में अनुवाद नहीं → en-US पर रोलबैक
- en-US में भी नहीं → मूल key लौटाएं

### 5.5 फ्रंटएंड i18n

- Flutter स्वयं निर्मित `AppTranslations` + `LocaleController` (GetX) का उपयोग करता है
- भाषा प्राथमिकता SharedPreferences में स्थायी होती है
- भाषा बदलते समय `Get.updateLocale()` से वैश्विक UI पुनः रेंडर होता है
- `StringResult` क्लास Dart के `toString()` का उपयोग करके स्वाभाविक इनलाइन सिंटैक्स प्राप्त करती है: `Text('${AppTranslations.t("key")}')`

## 6. मानक संस्करण नए डिज़ाइन

### 6.1 जोखिम नियंत्रण इंजन

महत्वपूर्ण धन संचालन से पहले बहु-परत नियम जाँच:

```
रिचार्ज/निकासी/विनिमय अनुरोध
  ↓
RiskService::check(userId, type, context)
  ├── IP ब्लैकलिस्ट जाँच (ip_blacklist) → block
  ├── बड़ी राशि असामान्यता जाँच (amount_anomaly) → warn
  ├── आवृत्ति जाँच (frequency) → warn/block
  └── गति जाँच (velocity) → block
  ↓
passed → सामान्य निष्पादन
warn   → लॉग रिकॉर्ड करें, निष्पादन जारी रखें
block  → संचालन अस्वीकार
```

नियम `game_risk_rule` तालिका में संग्रहीत होते हैं, कॉन्फ़िग JSON में, सीमा और क्रियाएँ गतिशील रूप से समायोजित की जा सकती हैं।

### 6.2 KYC वास्तविक नाम प्रमाणीकरण

तीन-स्तरीय प्रमाणीकरण प्रणाली:
- `default` — प्रमाणित नहीं, बुनियादी सीमाएँ
- `verified` — KYC समीक्षा स्वीकृत, सीमाएँ बढ़ीं + कम शुल्क
- `vip` — VIP स्तर, उच्चतम सीमाएँ + शून्य शुल्क

प्रमाणीकरण प्रक्रिया:
```
उपयोगकर्ता पहचान दस्तावेज़ जमा करता है → status=pending
प्रशासक समीक्षा → approve/reject
approve → उपयोगकर्ता स्वचालित रूप से verified स्तर पर उन्नत
reject → उपयोगकर्ता पुनः जमा कर सकता है
```

### 6.3 OAuth तृतीय-पक्ष लॉगिन

Google / Facebook / Apple लॉगिन समर्थित:

```
फ्रंटएंड OAuth बटन क्लिक करता है
  → GET /api/auth/oauth/{provider} → प्राधिकरण URL प्राप्त करें
  → तृतीय-पक्ष प्राधिकरण पेज पर जाएं → उपयोगकर्ता सहमति
  → कॉलबैक POST /api/auth/oauth/{provider}/callback
  → मौजूदा बाइंडिंग खोजें → सीधे लॉगिन
  → कोई बाइंडिंग नहीं → स्वचालित रूप से नया उपयोगकर्ता + बाइंडिंग + वॉलेट निर्माण
```

### 6.4 भुगतान कॉलबैक

```
तृतीय-पक्ष भुगतान पूर्ण → POST /api/payment/callback
  → provider श्वेतसूची सत्यापन (केवल stripe/paypal)
  → हस्ताक्षर सत्यापन fail-closed (secret/webhook_id कॉन्फ़िगर नहीं, हस्ताक्षर सत्यापन विफल, टाइमस्टैम्प ±300s से अधिक — सभी अस्वीकार)
  → कॉलबैक राशि और ऑर्डर राशि bccomp से मिलान (क्रॉस-चैनल दुरुपयोग रोकना)
  → ऑर्डर स्थिति confirmed अपडेट करें (लेनदेनित, जमा विफल पर रोलबैक)
  → UserWallet::addBalance जमा
  → Transaction रिकॉर्ड करें
  → RiskService::check जोखिम नियंत्रण जाँच
```

## 7. स्केलेबिलिटी डिज़ाइन

### 5.1 क्षैतिज स्केलिंग

admin/ और service/ दोनों बहु-worker प्रक्रियाओं का समर्थन करते हैं। Nginx रिवर्स प्रॉक्सी के साथ, क्षैतिज स्केलिंग के लिए कई मशीनें तैनात की जा सकती हैं:

```
Nginx (लोड बैलेंसिंग)
  ├── admin-1 (:8787)
  ├── admin-2 (:8787)
  ├── service-1 (:8788)
  └── service-2 (:8788)
```

### 5.2 मॉड्यूल विभाजन पथ

जब एकल service/ बाधा बन जाता है, निम्न पथ से विभाजित करें:

```
service/ (मोनोलिथ)
  → service-user/ (उपयोगकर्ता सेवा :8788)
  → service-wallet/ (वॉलेट सेवा :8789)
  → service-game/ (गेम सेवा :8790)
  → service-payment/ (भुगतान सेवा :8791)
```

विभाजन समय निर्धारण मानदंड:
- एक मॉड्यूल का QPS एकल मशीन की क्षमता से अधिक हो
- किसी मॉड्यूल को स्वतंत्र तकनीकी स्टैक या तैनाती रणनीति की आवश्यकता हो
- टीम का आकार विभिन्न मॉड्यूलों पर समानांतर विकास आवश्यक बनाने के लिए बड़ा हो जाए
